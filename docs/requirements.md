# OneDesk 第一个里程碑：需求汇总

本文件汇总用户的原始需求和全部补充要求（按收到顺序合并）。**每个会话开始前必须读完本文件**，与 CLAUDE.md、docs/architecture.md、docs/decisions.md 一起作为依据。冲突时：后来的补充要求 > 原始需求；接口摘要没写的由主会话决定（写进 decisions.md）。

---

## A. 目标与范围（原始需求）

OneDesk 是“内核 + 插件”的桌面应用框架，个人和企业日常工作的统一入口。第一版：可用、可扩展、外观专业。

内核只抽象三件事：资源、插件（提供类型、动作、视图等能力）、视图（宿主根据声明画出界面）。所有具体功能由插件提供，内核不认识任何具体功能。

**范围**
1. 骨架：Tauri 2 + React + TypeScript，Rust 后端，本地 SQLite。包名与项目名统一 `onedesk`。
2. 内核：
   - 统一资源表：id、kind、name、group、tags、description、body（JSON）、visibility、aiVisible、version、createdAt、updatedAt、origin。
   - 资源增删改查；全文搜索（名称、描述、标签、body 文本）。
   - 分组与标签；集合只做手动的（按标签或类型），智能集合下一阶段。
   - 插件宿主：加载、启用、停用；读清单；注册 kind、action、view；校验 apiVersion。
   - 菜单：每个资源是一个菜单项；点击进入由 kind 的 schema 和默认视图生成的页面。
   - 通用视图：表单（按 schema 生成输入）、表格、文本、链接。
   - 动作执行：宿主调用 action.run，显示输出（文本、表格、链接、无），执行中和失败都有明确状态。
   - 宿主 API：resources、actions、ui、storage、notify、context；network、secrets 见补充要求（secrets 用钥匙串实现）。
3. 内置插件（与外部插件完全相同的公开接口）：
   - 网址：kind `link`，动作 `open`（系统浏览器）。浏览器配置文件只留字段。
   - 笔记：kind `note`，视图 `markdown`（阅读态）。
   - 提示词：kind `prompt`，schema 含参数定义，动作 `copy`（替换参数后复制到剪贴板）。
   - HTTP 请求：kind `http-request`，动作 `send`，视图 `response`；经宿主 network 能力发请求。
4. 不做：数据库类插件、发布、订阅与共享、AI 接口（MCP）、多设备同步、账户登录（只在接口预留位置）。

**接口摘要（用户原文）**：本次工作的唯一依据；实现见 `src/plugin-api`，与摘要的差异见 decisions.md D130。

清单（manifest）：
- id（全局唯一，如 org.example.link）、name、version、description、icon
- apiVersion：当前为 "1"
- provides：提供的 kind、action、view 列表
- requires：需要的宿主能力（network、secrets、其他插件的数据源等）
- settings：设置项定义，宿主据此画设置表单

资源条目（所有插件共用）：
- id、kind、name、group、tags、description
- body：按 kind 定义的 JSON
- visibility：private 或 public；aiVisible：布尔值
- version、createdAt、updatedAt、origin（original、subscribed、copied 之一）

kind（资源类型）：
- schema：字段列表，每个字段有名字、类型（text、number、url、reference、parameter 等）、是否必填
- defaultAction：点击时默认执行的动作 id
- views：可用视图 id 列表
- describe(resource)：返回给 AI 看的摘要和用途

action（动作）：
- id、label、input（参数定义）、output（text、table、file、link、none 之一）
- run(context, input)：执行并返回输出，不直接操作界面

view：
- render(resource, state)：返回声明式的视图树，由宿主画出来；插件不直接操作 DOM
- 视图树只用四种节点：form（字段列表）、table（列和行）、text（纯文本或 markdown）、link（href 和文字）

宿主 API（插件只能通过这些入口做事）：
- resources：按 id、kind、标签、集合读写自己类型的资源
- collections：创建和读取集合
- actions：调用其他插件提供的动作
- events：订阅资源变化、动作完成等事件
- ui：注册视图、菜单项
- storage：插件自己的键值存储，互不干扰
- secrets：按名字读取已授权的密钥（本里程碑占位）
- network：发送请求，地址必须在清单里声明（本里程碑占位）
- notify：给用户显示消息
- context：当前工作区、当前用户、调用来源（手动、定时、AI）

生命周期：安装 → 启用 → 激活（注册自己提供的能力）→ 停用 → 卸载。停用后，资源保留，但它的视图和动作不再出现。

## B. 界面与体验（原始需求）

- 第一眼像成熟、可信赖的专业软件，细节经得起推敲。
- 设计 token（颜色、字号、间距、圆角、阴影、动效时长）全部是 CSS 变量，集中在一个文件；组件只引用 token。
- 颜色：中性色为主，一个品牌强调色，语义色（成功、警告、错误、信息）。浅色/深色完整，跟随系统且可手动切换。对比度 ≥ WCAG AA。
- 字体：系统无衬线；字号阶梯 12/13/14/16/20/24，正文约 14px；数字用等宽或表格数字。
- 间距：4px 栅格；密度两档（舒适、紧凑），可切换。
- 布局：左侧固定菜单（资源目录，可分组、可折叠、可拖动排序），右侧页面内容，顶部全局搜索和主要操作。页面统一：标题区、操作区、内容区。最小 1280px 宽。
- 组件：按钮、输入框、下拉、表格、对话框、抽屉、标签页、徽标、提示条、吐司、菜单、工具提示。风格统一（圆角、阴影、边框、悬停、按下）。Radix 等无样式库做交互，外观全部用自己的 token。
- 动效：克制，只用于展开、切换、反馈，120–200ms，无弹跳。
- 键盘：全部操作可键盘完成；⌘K/Ctrl+K 命令面板（搜索资源、执行动作、切换页面）；焦点清晰可见。
- 状态：每个页面有加载中、空状态、错误状态。空状态一句话说明下一步，不放插图。错误给原因和处理方式。
- 停用的插件和失效的资源灰色显示，不隐藏（与验收第 3 条的协调见 D15）；动作执行中显示进度，失败用红色文字说明原因。
- 文案：简短、准确、动词开头，中文为主，集中管理便于多语言。
- 图标：一套统一线性图标，线宽一致。
- 不做：渐变背景、大面积强调色块、装饰性插图、弹跳动画、过度阴影。

## C. 工作要求（原始需求）

- 先写 architecture.md 草稿，再编码。先搭 token 和基础组件，再做页面；页面只能用组件拼，不写一次性样式。
- 顺序：存储层 → 资源增删改查 → 插件宿主 → 设计系统与基础组件 → 菜单和通用视图 → 内置插件 → 搜索和命令面板。每步可运行、有测试。
- 内核不得出现具体插件的名字或逻辑。内置插件只能走公开接口。
- 小步提交，提交信息写清楚做了什么、为什么。不确定就选最简单的做法，记入 decisions.md。不扩大范围。
- 完成后汇报：运行方式、测试结果、截图（浅色和深色各一张，覆盖菜单、表单、表格、空状态、错误状态）、已知限制、与接口摘要不一致的地方。

## D. 验收标准（原始需求）

1. 启动应用，菜单列出所有资源，界面符合设计要求。
2. 新建网址、提示词、笔记、HTTP 请求资源，各自点击进入正确页面并能使用。
3. 停用“HTTP 请求”插件后，菜单项消失、数据保留；重新启用后恢复。
4. 搜索能按名称、标签和正文找到资源；⌘K 命令面板可用。
5. 浅色和深色主题完整，主要页面无明显对比度或对齐问题。
6. 内核测试覆盖：资源增删改查、插件加载与清单校验、动作执行。

## E. Claude Code 工作方式（补充 1）

- CLAUDE.md 简短，只写每次都需要的；细节放 docs。
- 设计类工作（接口定稿、架构、里程碑拆解）先出方案再执行。
- 项目命令 `.claude/commands/`：`/check`、`/new-plugin`、`/review-ui`。
- `.claude/settings.json` 允许常用命令自动执行。
- 独立检查用子代理/新会话审查：内核是否混入插件逻辑；界面是否符合设计。审查者不看实现者推理，只看代码和接口摘要。
- 每步：先 `/check`，通过再提交。会话结束前把新决定写进 decisions.md，更新 CLAUDE.md 过时部分。

## F. 多会话协作（补充 2）

- 主会话：接口定稿、架构、任务拆分、合并审核、取舍。内核会话（Fable/Opus）、设计系统会话（Opus）、插件会话（Sonnet）、测试与样板会话（Haiku）、审查会话（Opus，不看实现推理）。需要时可开 Fable 会话协助架构等重要工作。
- 每个会话一个模块，独立分支/worktree；一个文件同一时间只有一个写入者；任务说明写清可改/不可改的文件。
- 接口在里程碑内不变；改接口只能由主会话决定并写进 decisions.md，再通知所有会话。
- 会话之间只通过 `docs/handoff/` 交接文件交流：完成了什么、改了哪些文件、还缺什么、需要谁确认。不清楚的先在交接文件提问，不要猜。
- 任务说明格式：目标、允许修改的文件、依赖的接口和文件（只读）、完成标准、交付物。
- 顺序：主会话先完成接口与内核骨架 → 插件和界面并行。合并前先审查，再由主会话合并，合并后跑完整 `/check`。冲突以接口摘要为准。
- 合并前检查：只改了分配范围内的文件；测试和检查通过；内核无具体插件名字或逻辑；没有绕过 token 写样式；交接文件已更新；decisions.md 已记录。

## G. 补充要求（补充 3，优先级高于前文）

1. **环境**：仅 macOS（Apple Silicon 优先，Intel 也能构建），最低版本写进 architecture.md。Node LTS + pnpm，Rust stable，版本写进 `.nvmrc`/engines 和 `rust-toolchain.toml`。根目录一条命令完成首次安装和启动（写进 CLAUDE.md）。
2. **数据**：数据库 `~/Library/Application Support/onedesk/onedesk.db`。设置里“导出全部数据”：文件夹含 `resources.json`、`collections.json`、`manifest.json`（版本、导出时间）、附件文件夹；不依赖本应用可直接阅读。“导入”：读同样结构，相同 id 询问覆盖或跳过。每次启动自动保留最近 7 份快照到 `backups/`。
3. **迁移**：版本号存数据库（`schema_version`）。每次改结构新增迁移文件（编号递增），不改已发布的。迁移在事务中执行，失败回滚并明确提示，不允许在半升级状态下使用。每个迁移都有从上一版本升级、数据不丢的测试。
4. **插件位置**：内置插件随应用发布；外部插件在 `~/Library/Application Support/onedesk/plugins/<文件夹>/manifest.json`。启动时扫描；清单错误、apiVersion 不兼容、id 重复的不加载，在设置页列出原因，不影响其他插件。内置与外部走同一条加载路径，只是来源不同。
5. **测试分层**：单元（资源 CRUD、清单校验、视图树、搜索；内核核心覆盖率 ≥ 80%）；集成（插件宿主完整生命周期、迁移）；界面测试（新建资源、打开菜单项、运行动作、搜索、切换主题，用端到端工具驱动）；视觉检查（菜单、表单、表格、空状态、错误状态，浅/深各一张，存 `docs/screenshots/`，界面改动后更新）。全部由 `/check` 运行，失败不许提交。
6. **性能**：冷启动到看到菜单 < 2 秒；1 万条资源搜索 < 200ms；动作执行时界面不冻结，显示进度。性能测试放进集成测试，有数据可对比。
7. **密钥**：只存 macOS 钥匙串，经 `secrets` 接口按名字读取；数据库、清单、导出中不能有明文。设置页可添加、修改、删除密钥。删除插件时询问是否同时删除它的密钥。
8. **依赖**：新增前在 decisions.md 写用途、替代方案、许可证；只用 MIT/Apache-2.0/BSD 等宽松许可证，其他需主会话确认；能不加就不加。
9. **阻塞**：接口不够、需求冲突、环境问题时不自行扩展接口或改范围；在 `docs/handoff/` 写阻塞说明（遇到什么、试过什么、需要什么决定），先做不依赖它的部分。
10. **不扩大范围**：开始前读 CLAUDE.md 和任务说明；范围外的问题只记到 `docs/handoff/todo.md`。

## H. 来自已有开发的经验（补充 4，必须遵守）

- **验证**：每次改动后真正运行，而不只是过测试；验收包括实际启动应用、点一遍主要流程。没运行过、没看到结果、测试没过，都如实写出，不说“完成”。改完先确认能编译再做下一步；写完一段立即跑对应测试和 lint。
- **文件与路径**：用完整路径，使用前确认目录存在（`~/Library/Application Support` 不是 `/Library/Application Support`）。写完 JSON 立即 `python3 -m json.tool` 校验。不要假设用户界面有某个菜单或选项。
- **编辑冲突**：编辑前先读最新内容；同一文件同一时间一个写入者；用脚本改了文件也要重新读取确认。
- **测试安全**：会删表或重建数据的集成测试只在专门测试库上运行，并用环境变量显式开启；测试代码拒绝在名字像正式库的数据库上运行。
- **Rust/Tauri**：多个可执行文件时 `Cargo.toml` 设 `default-run`；`DROP COLUMN` 等单独写迁移并用旧库测试；每次修改后 `cargo clippy --all-targets`，警告也要处理。
- **设计教训**：启发式安全边界“宁可误拒，不可误放”，每种拒绝都有测试；临时存放（如密码放 localStorage）要在文档标记待迁移和期限；参数语法统一（`{{name}}`），有 lint 或测试检查占位符；生成的映射文件随源码重新生成，歧义时输出警告不静默猜测；文档随代码更新（CLAUDE.md 代码地图不能过时）。
- **沟通**：对用户的说明简短，先结论后步骤；命令每条一个代码块，不夹输出。讨论设想和开发是两件事（本里程碑用户已明确要求开发）。
- **用户偏好**：用户通常不在电脑前，**尽量不要问用户**，自行决定并记录到 decisions.md。

## I. 里程碑二需求（用户补充，优先级高于 A–H）

里程碑一只做了骨架、内核、四个内置插件和基础界面。本节是下一个里程碑的需求，与前文冲突时以本节为准。

### I.0 长期方向

- 目标：一个 OneDesk 承载个人和工作中日常使用的大部分软件的功能，逐步替代这些软件。
- 每一类软件的功能由插件提供；替代的顺序按用户日常使用的频率决定，每完成一类，记入决定记录。
- 各阶段的需求以本文件为准；方向不因单个阶段的范围而改变。

### I.0b 标签页与配置

- 标签页不是独立数据，只是资源的显示。标签页的开合和顺序属于界面状态，不进入版本化，也不参与同步。
- 工作区有两棵独立的树，机制相同（类型化参数、父子结构、子节点继承并可覆盖、可版本化、可标记同步）：
  - **环境树**：每个环境是一个节点，控制某个标签页内的运行条件。
  - **工作区配置树**：每个配置项是一个节点，控制整个工作区，例如深色或浅色、菜单语言。
- 两棵树的区别只在控制范围：环境树控制标签页，工作区配置树控制工作区。
- 两棵树互不包含对方的节点。
- 插件也是一棵树（插件树），与资源树、环境树、配置树互不包含。点击插件，在标签页中打开该插件的页面。页面包含：说明、版本、启用或停用开关、该插件的设置项（来自清单的 settings）、权限声明（requires）、加载状态和错误原因、它提供的类型和动作。启用状态按工作区保存（D143）。

### I.0d 结果区

- 每个标签页都有结果区，放在页面的下方，可以拖动调整高度、可以收起。运行动作（查询、命令、请求、导入等）的结果显示在这里，不另外弹窗。
- 结果区按输出类型显示：文本、表格、链接、文件列表；表格支持排序和列宽调整（见 I.7）。
- 结果保存在该标签页的执行历史中（见 I.5），可以回看、复用参数再次执行、导出。
- 动作执行中显示进度；失败的原因显示在结果区，不闪现后消失。
- 结果区可以把结果交给 AI 分析（里程碑二的 AI 接口）。发送的内容先以 Markdown 形式准备，用户可以编辑后再发送。

### I.0f 占位符

- 占位符由插件定义：插件决定用什么语法、占位符的名字和类型，以及它从哪里取值。核心不规定统一的占位符语法。
- 核心只提供一种能力：按名字从当前环境取值（环境树的父子覆盖规则同样适用），取不到时交给插件处理（例如让用户在表单中填写）。
- 插件声明自己接受哪些占位符（名字、类型、说明），这些声明用于生成参数表单和悬停说明。
- 不同插件的占位符互不冲突：同一段文字在不同插件里可以有不同含义，因为它由各自的插件解释。
- 例：SQL 插件使用 `:name`（沿用 sqlpool，D177）；提示词插件可以用自己的语法；网址插件可以用另一种语法。

### I.0e 扩展点与依赖

- 树和标签页的类型是接口的扩展点：插件可以提供新的树类型、标签页类型、结果区的输出类型。
- 插件之间通过依赖关系（`requires.plugins`）直接使用对方提供的树和标签页，不需要每个插件都自己定义一套。例如，提供树的插件（如 SQL 插件的资源树）被依赖后，依赖它的插件直接挂到这棵树上，并使用它的标签页和结果区。
- 依赖只能使用对方明确声明提供的扩展点，不能直接访问对方的内部实现。
- 扩展点的接口属于冻结的插件接口，新增扩展点需要先写决定（见 D175）。

### I.0h 工具栏与状态栏

框架有五处工具栏和一处状态栏。插件只能往自己的标签页的操作区放按钮，不能改框架的工具栏。

**1. 顶部栏（整个窗口，一条）**
- 左：工作区名称（点开切换或新建工作区）。
- 中：全局搜索框（⌘K 聚焦）。
- 右：新建（下拉：各类型资源、导入）、命令面板入口（⌘⇧P）、设置入口。

**2. 树的工具栏（每棵树的顶部，一条）**
- 全部展开、全部折叠。
- 新建分组（在当前选中的节点下面）。
- 树内过滤（输入即过滤节点名称）。
- 每棵树的工具栏只放与这棵树有关的操作。

**3. 标签栏（窗口的标签页上方，一条）**
- 标签列表：每个标签前有类型图标；可以关闭、固定。
- 右端：关闭全部标签、显示全部标签（列表）。

**4. 标签页的操作区（每个标签页顶部）**
- 由该标签页所属的插件决定按钮，框架只保证位置和样式一致。
- 动作按钮最多显示三到四个，其余放进“更多”。

**5. 结果区的工具栏（结果区顶部，一条）**
- 页签：由插件决定，框架提供切换的样式。
- 右端：收起、展开、清空结果。

**状态栏（窗口最底部，一条，细）**
- 左：当前工作区、当前标签页的环境、当前数据源（如有）。
- 中：当前动作的进度或最近一次结果的摘要。
- 右：同步状态（D165 之后显示）、版本化状态（git 开启时显示）、界面语言。

### I.0c 框架原则：尽可能干净

- 内核只保留通用机制：资源、插件、树、标签页、参数、历史、权限。具体功能全部由插件提供。
- 一个概念只用一种机制。环境、工作区配置、插件设置都用同一套参数和树。
- 不为个别功能开特例。新功能先问：能不能用现有机制表达。
- 每个设置放在它控制的对象上：工作区的放在工作区，插件的放在插件页，环境的放在环境树。
- 界面的入口只放在对象自己的页面里，不增加额外的管理页面。
- 所有功能尽量放在树和标签页这两种结构中。内容要能容纳大量条目，操作要简单。尽量少用对话框；必须用的（如系统的文件选择），只在必要时出现。

### I.0a 工作区、工作区配置定义、工作区环境

三个概念分开定义，不互相替代：

| | 工作区 | 工作区配置定义 | 工作区环境 |
|---|---|---|---|
| 是什么 | 一个独立的数据和运行单元（一个实例） | 新建工作区时使用的模板 | 工作区内的一组参数和保护设置，组成一棵树 |
| 作用 | 数据隔离的边界，例如某家公司的账；决定本工作区的设置（深色或浅色、菜单语言等） | 让新建工作区更快，例如“家庭版模板”“企业版模板” | 在标签页内为资源选择运行条件，例如测试或正式 |
| 存放位置 | 应用里的一个独立数据库文件 | 应用级数据，不属于任何工作区 | 该工作区的数据库文件里 |
| 切换方式 | 整个窗口切换，或新开窗口 | 不切换；新建工作区时选用 | 在标签页内选择；每个标签页可以有自己的环境 |
| 能否跨工作区 | 不能（隔离） | 可以被多个工作区复用 | 不能，只属于它所在的工作区 |
| 修改影响 | 只影响自己 | 只影响以后新建的工作区，不改已有工作区 | 只影响该工作区内使用它的资源 |

补充规则：

- 工作区配置定义只描述“如何开始”：默认启用的插件、默认设置覆盖、默认环境树。它不包含任何数据。
- 工作区的插件启用状态由工作区决定。工作区环境只能在工作区已启用的插件范围内，进一步停用插件，不能启用工作区没有启用的插件。
- 设置只属于工作区，保存在该工作区自己的数据库中，不存在全局设置层。深色或浅色、菜单语言都是工作区设置，只影响这个工作区。新建工作区时，设置的初始值可以来自工作区配置定义（模板），也可以复制一个现有工作区（通常是当前工作区）的设置。复制是一次性的，之后两个工作区的设置互不影响。
- 环境只在标签页内使用：每个标签页可以选择自己的环境，环境的参数只在该标签页内生效，不改变工作区设置，也不影响其他标签页。

### I.1 语言（国际化）

- 界面支持三种语言：中文（zh-CN）、日语（ja-JP）、英语（en-US）。
- 语言本身是插件：每种语言一个语言插件，由插件提供界面文字。
- 语言的选择在工作区配置树的“界面语言”项中完成。选项列表来自已安装并启用的语言插件；切换只影响该工作区。语言插件通过扩展点提供文字（D192）。
- 语言插件只提供外壳的通用文字（菜单、命令面板、设置页）。每个功能插件自带它的页面文字，每种语言一份；标签页的文字由该插件提供。某插件没有当前语言的文字时，回退到英语（D193）。界面默认语言是英语；缺失的文字回退到英语（D179、D191）。本节替代 C 节"文案中文为主"和 D134 的推迟决定。
- 所有界面文字不写死在代码中，集中在语言文件里，每种语言一份。
- 其他语言的文件暂时为空，但结构允许以后加入，不需要改代码。
- 缺失的翻译回退到英语，不显示空白，也不显示代码键名。
- 语言切换立即生效，并记住选择。
- 日期、数字、排序按当前语言格式化。
- 用户自己的资源内容（名称、描述、正文）保持原文，不被翻译。

### I.2 标签页

- 打开的资源和视图各占一个标签；标签可以关闭、固定，并记住打开状态。
- 标签前有类型图标，区分不同类型的资源。
- 标签栏高度足够；有一处能看到全部标签，并可一键关闭全部。
- 标签栏可以折叠。

### I.3 导航树

- 左侧栏是分组树，支持无限嵌套，像文件夹一样。
- 每棵树都有"全部展开"和"全部折叠"。
- 节点悬停时只改变自身背景色，不影响相邻节点，不产生跳动。
- 图标风格统一，图标与功能一致。
- 不设"未分组"节点。
- 分组可以被折叠、拖动排序；集合树、菜单树、环境树遵守同一规则。

### I.4 环境（第一个必须有的树）

- 环境是一组参数值，例如"测试环境""正式环境"，组成一棵树，层级不限。
- 子环境继承父环境的所有参数；子环境自己定义的同名参数覆盖父环境的值。
- 编辑区顶部面包屑显示完整的父环境链。
- 环境里能看到继承来的参数，并标明值来自哪一层；继承的参数可以在本环境覆盖。
- 环境有 description（说明）。
- 参数值属于环境，不写进资源本身；同一资源在不同环境下运行得到不同参数。
- 参数先从当前环境取，环境里没有的才让用户在表单中填写。
- 参数表不需要手动增删，参数由资源定义自动出现。
- 当前环境有清楚的标记，切换不需要重启。
- 每次修改参数值、说明或位置都记入历史（时间、操作者、改前值、改后值）。
- 可以从历史恢复到某次修改之前的状态；恢复本身也记入历史。
- 父环境修改参数后，子环境中对应的值标为"已变化"。
- 导出的 .sh 文件使用当前环境的参数值。
- 环境的所有设置都用参数表示，包括保护级别、密钥引用、允许访问的网络地址、启用的插件、版本化开关、AI 使用策略、视觉标记。不另设第二套配置机制。
- 参数有类型：文本、数字、布尔、列表、密钥引用（只存名字，值在钥匙串中）。
- 以保留前缀命名的参数由核心解释（例如 `protection.*`、`network.*`、`plugin.*`、`secret.*`）；其他参数只是值，由插件自行使用。
- 层叠时，保护类参数只能加严，不能放宽：父环境禁止导出，子环境不能重新允许。其他参数按“子环境覆盖父环境”处理。

### I.5 收藏、快捷键、历史与搜索

- 任何资源都可以收藏，收藏的排在最前；收藏是独立于标签的视图。
- ⌘K 打开搜索并聚焦到搜索框；⌘⇧P 打开命令面板，所有动作都能从这里找到；常用动作在菜单里显示快捷键。
- 每个可运行资源保留最近 200 次执行记录，记录参数、耗时、结果行数和错误；可以从历史复用参数再次执行。
- 点击历史记录必须打开对应的页面，不能只在当前窗口里变化。
- 扫描目录、同步、读取大量数据等慢操作放在后台，窗口不卡住，并显示进度或加载状态。
- 搜索：多个搜索词同时满足才算命中；很短的词也要能搜到。
- 外部目录同步：资源来自文件目录时，文件是源头。同步时重建索引，保留收藏、标签和历史；被删除的文件从搜索中消失，但历史保留。

### I.6 插件身份、版本与记录

- 每个插件有稳定 id（如 `org.example.http-request`）和发布版 id（如 `org.example.http-request@1.2.0`）。资源的类型用稳定 id 引用，升级插件不改变已有资源的类型。
- 依赖和引用写成"稳定 id + 版本范围"，如 `>=1.2 <2`。
- 同一插件的多个版本可以同时存在于本机，用于回滚；同一时间只启用一个。用户可以把插件固定在某个版本。
- 升级前保留旧版本，失败时可以回退；回退不删除资源。
- 每个资源记录 createdBy（创建它的发布版 id）和 updatedBy（最后编辑它的发布版 id）；每次编辑的历史也记录编辑者的发布版 id。
- 用户在核心界面直接编辑的，记录来源为"核心"；AI 发起的编辑，额外记录调用来源（手动、定时、AI）。
- 插件卸载后，资源上的记录保留，仍显示原插件 id 和版本。
- 插件规模按上万个设计：启动时只读取清单建立索引，插件在第一次使用时激活；插件搜索覆盖全部插件。

- 插件的分发、签名、信任和审核，由用户另外建设的系统负责，不在 OneDesk 中实现（见 D158）。OneDesk 只负责：读取标准的插件包，校验清单和接口版本，安装时展示权限，经用户确认后启用。

### I.7 界面细节（来自 sqlpool 中反复提出的要求）

- 所有分割线都可以拖动，拖动时光标统一、不选中文字；尺寸关闭后记住。
- 信息面板的宽度不随内容多少变化；用户拖过之后固定。
- 列表和表格的列可以排序，点表头三态切换（升序、降序、取消），表头有方向标记；列宽可拖动并记住。
- 表格竖线对齐，单元格之间没有多余空白。
- 字体使用系统字体，显示清晰不发虚；字号比里程碑一整体大一号。
- 错误信息放在结果区，不能闪现后消失。
- 不显示无用的提示文字；编辑区占满可用空间。
- 导出 CSV 时，没有设置目录则让用户选择；CSV 带 UTF-8 BOM，Excel 打开不乱码。
- 参数名后的说明用图标加悬停提示；环境自己的参数不需要这个图标。

### I.8 布局参照：VS Code

- 布局逐项对照 VS Code：左侧活动栏（图标切换侧边内容）、侧边栏（树，标题区带工具栏）、顶部标签栏（带图标、关闭按钮，未保存有标记）、标签下的面包屑、中间编辑区、底部可收起的面板、最底部的状态栏、命令面板。
- 所有分割线可以拖动，布局记住。
- 验收时逐项对照本条，不以"风格相似"代替。

### I.9 存储与版本化（git 为可选项，见 decisions.md D141）

- 默认存储是本应用自己的数据库（SQLite），不需要 git。
- git 是用户可选的版本化方式。用户在设置中决定是否启用，也可以随时关闭。
- 启用后，用户选择仓库位置：本地目录、远程 git 服务器，或 GitHub 仓库。
- 版本化的范围由用户按资源类型决定。每种类型可以单独开启或关闭；未开启的类型只存在数据库中，没有提交历史。
- 开启版本化的资源，每次保存（防抖后）生成一次提交，提交信息记录操作者（发布版 id 或“核心”）。历史、恢复、对比都基于提交。
- 关闭某类型的版本化后，已有提交保留在仓库中，不删除。重新开启时，历史从开启时刻开始，不回溯生成。
- 远程推送、拉取由用户触发或按用户设定的间隔进行。拉取产生冲突时，必须由用户处理，应用不静默覆盖。
- 推送到远程或 GitHub 会把版本化资源的内容发送出去。设置页在首次推送前必须明确提示，并列出将被推送的资源类型。
- 密钥永远不进入 git 仓库，仍只存在钥匙串中。
- git 通过调用系统 git 命令访问（见 D140）；可以设置外部 git 可执行文件的路径。
- 提交防抖默认 5 秒；切换资源、关闭窗口或手动“立即保存版本”时立即提交；设置中可调 2–60 秒（见 D142）。
- 拉取冲突：冲突资源标为有冲突并只读，其他资源照常使用；在“设置 → 版本化 → 冲突”中并排比较本地与远程，选择采用本地、采用远程，或手动合并（见 D142）。
- 仓库不可用时应用照常工作，提交排队并在顶部提示，恢复后补提交。
- 仓库中的改动（无论来自手动编辑、另一台设备或其他 git 工具）视为合法，自动更新到数据库。若该资源在数据库中没有尚未提交的本地改动，直接采用仓库的版本。若两边都有改动，走冲突流程（D142）。（D203，取代 D142 中“仓库被外部改动时不自动采纳”的说法。）

### I.10 工作区（一份功能，每个工作区一个数据库文件）

- 应用程序和功能只有一份。
- 每个工作区有自己独立的数据库文件（SQLite）。数据、搜索索引、执行历史、环境、收藏都保存在该文件中。工作区之间彻底隔离：不允许跨工作区的查询、统计、搜索或引用。
- 应用级数据（已下载的插件包、工作区列表、工作区配置定义）
- 跨工作区只允许显式的导出和导入：把一个工作区导出为文件，再导入到另一个工作区，导入的内容作为新数据。
- 设置只属于工作区，不存在全局设置层。
- 插件：第一次安装时下载一次，保存在应用中。其他工作区启用同一插件时直接使用已下载的版本，不重复下载。插件的启用状态和版本固定都按工作区决定。
- 工作区以窗口为单位切换，与 VS Code 一致：
  - 在当前窗口打开工作区：整个窗口切换为该工作区，菜单、标签页、搜索范围全部随之变化。
  - 新建窗口打开工作区：另开一个窗口，两个工作区同时运行。
  - 每个窗口同一时间只属于一个工作区，不在窗口内用标签切换工作区。
- 密钥按工作区标识存放在钥匙串中，工作区之间互不可读。
- 版本化（git）设置属于工作区，不属于全局。
- 分支是高级功能，默认关闭。工作区设置中有“高级模式”开关，默认关闭；关闭时界面不显示分支的创建、切换、合并，只保留主线上的历史、恢复和对比。开启后才显示分支功能。
- 分支的用途是草稿和发布：修改先在草稿分支上进行，确认后合并到主线。
- git 链接是工作区设置的一部分：仓库位置（本地、远程或 GitHub）、外部 git 可执行文件路径、哪些资源类型纳入版本化，都保存在该工作区的设置中。
- 删除工作区会删除其数据库文件，操作前必须二次确认并说明不可撤销；外部 git 仓库不受影响。
- 家庭版是新建工作区时的模板，预先启用家庭相关插件。版本只决定模板，不决定安装包数量。

- 一个工作区基本等于一个实例：它有自己的数据文件、设置覆盖、插件启用状态，是一个独立的运行单元。实例可以是本地的，也可以连接到远程实例（例如某公司的服务）；连接方式属于工作区的设置。

- 不同性质的工作内容分开，各自放在一个工作区里。例如给多家公司记账的财务人员，每家公司一个工作区。
- 工作区是可选的。首次使用时只有一个工作区；只有当内容差别很大时才需要新建。内容单一的用户（例如家庭主妇）用一个工作区即可，不需要分开。

### I.10a 引用与搜索（与别人的做法一致）

- 工作区内的搜索与别人在常见软件中的做法一致：⌘K 打开、按类型过滤、模糊匹配、结果按相关度和最近使用排序。
- 引用别人的资源只能通过发布和订阅：对方发布后，你订阅得到的是一份跟随更新的副本，并标明来源。不能直接查询对方的工作区，也不能在搜索中看到未发布的内容。
- 资源之间的引用写法与常见链接一致（Markdown 链接，以及 `[[名称]]` 形式的内部引用）。引用指向被删除或未订阅的资源时，显示为失效引用，不静默消失。
- 引用跨工作区时只能是订阅形式，不构成跨工作区的查询或统计。

### I.10b 导入硬盘资源插件（基础版）

- 插件 kind 为 `disk-file`，每个文件或文件夹导入为一条资源，记录：名称、完整路径、大小、修改时间、扩展名。资源只保存路径和信息，不复制文件内容。
- 导入动作：用户选择一个文件夹，插件列出其中的文件（可选是否包含子文件夹），为每个文件创建资源，分组名为所在文件夹名。重复导入同一路径时，更新已有资源，不重复创建。
- 资源动作：在系统中显示（Finder 中定位）、用默认应用打开。文件不存在时，资源显示为失效，不删除。
- 基础版不读取文件内容，不做全文索引；文本类文件的内容导入留给后续版本。
- 需要宿主新增能力 `files`（见 decisions.md D157）：选择文件夹、列出目录、读取文件信息、在系统中显示和打开。插件须在清单中声明 `requires.files`，安装时由用户确认。

### I.10b-2 文件管理（替代系统资源管理器）

- OneDesk 提供完整的文件操作，替代系统的资源管理器：浏览文件夹、新建文件夹和文件、重命名、移动、复制、删除、打开、在系统中显示、搜索文件名。
- 文件以文件树和列表呈现：文件夹是树的节点，可以展开和折叠；右侧或标签页中列出当前文件夹的内容。文件树是独立的一棵树，与资源树、环境树等互不包含（D147）。
- 删除默认移到废纸篓，不直接永久删除；永久删除需要二次确认，并说明不可撤销。
- 移动和复制遇到同名文件时，由用户选择覆盖、跳过或保留两份。
- 对文件的操作全部在标签页中完成，结果显示在结果区（I.0d）。
- 文件操作只能在用户授权的文件夹内进行。授权范围在硬盘文件插件的页面中定义：可以有多个授权文件夹，以列表管理（增加、查看、修改、移除）。移除授权不删除已登记的资源，也不删除文件本身。
- 硬盘文件插件（I.10b）是这项能力的一部分：导入路径是“登记”，文件管理是“操作”。

### I.10c 网页访问（本机作为网页服务）

- 应用可以开启“网页访问”，把自己的界面和功能以网页的形式提供。默认关闭。
- 网页访问由运行中的应用提供，文件、git、钥匙串等功能都在这台电脑上执行，网页只负责显示和操作。
- 默认只允许本机访问。用户开启后，可以允许同一局域网内的设备访问，地址为电脑的局域网地址加端口。
- 允许局域网访问时，必须设置访问口令；口令存放在钥匙串中，不写在网页或配置文件里。连接使用加密方式。
- 远程访问（不在同一局域网）不在本范围内，另行设计。
- 应用未运行时，网页访问不可用。
- 前端增加一个通过网络访问本机服务的适配，界面代码与桌面版共用。

### I.10d 家庭服务器（可选）

- 用户可以在家里放一台一直开着的服务器（迷你主机或 NAS）。服务器运行 OneDesk 的无界面模式，不需要显示器。
- 服务器提供：网页访问（见 I.10c），git 远程仓库（用于版本化资源的同步和备份），以及定时备份。
- 各设备（电脑、手机浏览器）通过局域网访问服务器；设备之间的数据同步，以服务器为中心，通过 git 推送和拉取。
- 服务器本身也是一个工作区所在的设备；工作区的数据库只在它所属的设备上保存一份，其他设备通过 git 得到副本。
- 在外面访问家里的服务器，需要 VPN 之类的方式，不在本范围内，另行设计。
- 服务器系统（macOS 或 Linux）待确认。

### I.12 待设计的需求（只列要求，设计另行进行）

- **数据源**：每条连接保存哪些字段；密钥只保存名字；查询只能在只读方式下执行；有超时和行数上限；连接失败要有原因提示。
- **同步文件夹**：资源、环境、工作区配置如何保存成文件；多台设备打开同一文件夹时如何对齐；冲突时保留哪一份、备份放在哪里。
- **环境保护**：加严的规则在界面上如何表现；被保护的标签页有什么提示。
- **工作区生命周期**：创建、从模板或现有工作区复制设置、切换、删除（删除要确认）、导出与导入。
- **网页访问**：服务器无界面的启动方式；访问口令的设置和修改流程。
- **AI 分析**：结果如何发送给 AI；发送内容如何预览和编辑；分析结果如何保存，并与对应的执行记录关联。
- **家庭服务器**：安装、升级、备份的操作方式。
- **外部服务器**：设备如何找到家里的服务器，如何连接（见 docs/design/external-server.md）。

### I.10f 综合插件

- 综合插件提供一种树节点（综合节点）。综合节点可以放在树的任意分组下，节点下面可以放入任意插件的资源（网址、提示词、SQL、命令、文件等），按用户排列。
- 综合节点可以嵌套，节点内的资源可以增加、移除、排序；资源本身不被复制，移除综合节点内的引用不删除资源。
- 点开综合节点，在标签页中显示其中所有资源的列表，按类型显示图标，点击某一条在标签页中打开该资源。
- 与集合的区别：集合按条件自动收集；综合节点由用户手动排列，是一组明确放在一起的资源。
- 综合插件是第一期插件之一（D186）。

### I.0g 拖拽由插件决定

- 框架只提供拖拽机制：拖动源、放置目标、拖动时的视觉反馈、取消。
- 每个插件决定自己的拖拽行为：哪些节点或条目可以拖；拖到哪里有效；放下后做什么（移动、复制、加入综合节点、打开，或不接受）。
- 框架不假设拖拽的含义。同样的拖动，在资源树是移动，在综合节点里可能是加入。
- 拖动无效的位置，框架统一显示“不可放置”的视觉提示，不由插件另做。

### I.10g 包容性测试：Vioros 接入

- Vioros 是一个正式的独立系统，保持原样，不为接入 OneDesk 而改动它的仓库或发布方式。
- 接入的目的是测试 OneDesk 的包容性：能否在不改动内核的前提下，把一个完整的外部系统拆成插件接入。
- 接入的方式是插件，不是嵌入整个应用。插件通过 Vioros 的网关接口工作，界面用 OneDesk 的树、标签页、结果区、视图。
- Vioros 的功能对应（见 D188 的对照）：对象存储树、列表（浏览、删除、改名）、视频下载（取信息、下载、取消）、上传、播放、设置。
- yt-dlp 不随 OneDesk 主程序打包。它随 Vioros 插件一起下载：插件清单声明所需的外部程序、固定版本和校验值；安装时下载并校验，校验失败则插件不启用，并说明原因。
- 接入过程中发现的框架缺口，逐条记入决定记录，不在插件中绕过。

### I.13 审计记录

- 每个工作区有一份审计记录，保存在该工作区的数据库中，只追加、不修改、不删除。
- 记录的内容：时间、操作者（用户、核心、插件及其发布版 id、AI、外部 git 改动、同步）、操作类型、对象、改动前后的摘要、结果（成功或失败及原因）。
- 记录的操作类型至少包括：创建、修改、删除、恢复、导入、导出、冲突的解决、插件的安装、启用、停用、升级、卸载、设置的修改、权限或授权的变更（如硬盘文件的授权文件夹）、git 推送和拉取、仓库中改动的自动采纳、网页访问的开启和关闭、工作区的创建和删除。
- 密钥的值、访问口令的值永远不写入审计记录，只记录操作本身。
- 审计记录不随版本化提交；导出工作区时包含审计记录。
- 审计记录在工作区配置树的“审计”页中查看：可以按时间、操作者、操作类型过滤，可以导出为文件。（默认）
- 审计记录的保留期限，默认保留全部，用户可以手动导出后清理。（默认，待确认）

### I.10h 应用整合：本地插件调用外部 API

- 本地插件提供页面和逻辑：页面由插件的视图定义，动作由插件的逻辑执行。插件在本机运行，页面在标签页中显示。
- 插件调用的外部系统，通过一条“API 连接”资源定义：地址（写入白名单，仅允许访问它）、认证方式、密钥引用（只存名字，值在钥匙串）。同一插件可以有多条连接，例如测试和正式。
- 连接资源放在对应的树中（与数据源相同的做法，D168），可以分组、搜索、设置环境。
- 每次调用外部 API 的记录进入该工作区的审计记录（I.13）。
- 调用的结果显示在结果区；失败原因显示在结果区，不弹窗。
- 插件只能通过宿主的网络能力调用白名单中的地址，不能直接访问网络。
- 视图树的节点类型可以扩展：核心提供基础节点（表单、表格、文本、链接），插件可以提供新的节点类型（如播放器）。视频播放等特殊页面既可以是插件提供的视图节点，也可以是插件提供的标签页类型（扩展点，D175）（D206，已更正）。
