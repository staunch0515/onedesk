依据：`kernel-design.md`（内核设计，已批准方向）、`sqlpool-parity.md` 和 `vioros-parity.md`（两份验收条件，已确认）、阶段 0 的结果（界面原型、技术小样）。

## 1. 目标

做出一个内核加插件的工作台，并用两件事证明它成功：

1. sqlpool 的 90 项功能全部能用插件做出来（`sqlpool-parity.md`）。
2. Vioros 的 56 项功能全部能用一个插件做出来（`vioros-parity.md`）。

内核里不出现任何 SQL、数据库、ssh、视频、存储桶的字样。

## 3. 原型在后面怎么用

**它能加快什么**

- 原型的界面代码就是将来的外壳，不是画出来看看就扔的图。它只通过一个“协议客户端”取数据，现在对面接的是假数据。后面的工作是把假数据一块一块换成真内核，界面代码留用。
- 所以外壳这部分的工作量大约省掉一多半：布局、树、标签页、页面框架、结果区、状态栏、任务面板、环境页、插件页、审计页都已经有了。
- 假数据那一侧还起到“内核该返回什么”的样例作用，写内核时有具体的东西可对。

**它能保证什么**

- 原型有 24 项界面自动检查和一组截图。每换一块真数据，这些检查和截图都要重跑，样子变了会被发现。
- 外观只来自设计 token 和基础组件，页面里不允许写一次性样式（自动检查），所以不会越写越走样。

**它不能保证什么**

- 内核（阶段 1 和 3）不会因为原型而变快，那是全新的工作。
- 原型里的“协议”是做界面时临时定的，和内核设计不完全一致。阶段 2 要先把两边对齐，以 Rust 一侧为准生成类型，界面跟着改。这一步有返工。
- 原型只在 Chromium 里验证过。桌面窗口用的是另一种浏览器内核，编辑器和日期控件可能要调整。

## 4. 阶段

每个阶段的“规模”是相对值（小、中、大），不是工期承诺。

### 阶段 1：内核基础（规模：大）

- **做什么**：Rust 内核库。工作区文件夹与数据库、迁移（含第一版旧库升级）、统一写入管线（操作者、事务、历史、审计、事件）、资源与树、删除与恢复、参数与环境、策略（只能加严）、搜索（全文索引）、引用、收藏、密钥、导出导入、启动快照。
- **做完你能看到什么**：没有界面。能看到的是测试报告和性能数字。
- **验收**：内核测试覆盖率 ≥ 80%；1 万条搜索 < 200 毫秒；第一版旧库升级不丢数据；每一种越权有“被拒绝”的测试。
- **依赖**：无。

### 阶段 2：进程、协议，原型接上真内核（规模：中）

- **做什么**：
  - 主进程和工作进程；崩溃重启；文件锁。
  - 协议：以 Rust 为准生成 TS 类型；把原型里的协议对齐过来。
  - 把原型里不依赖插件的部分换成真数据：资源树、环境树、配置树、收藏、已删除；环境页、配置页、审计页、信息面板、搜索。
  - 在真正的桌面窗口里跑起来；空闲机器上重测延迟。
- **做完你能看到什么**：打开桌面应用，原型里的树和环境页是真的了。新建分组、拖动、改环境参数、看历史、恢复，重启后都还在。
- **验收**：原型的界面检查在真内核上全过；截图与原型一致；杀掉工作进程能自动恢复且数据完整。
- **依赖**：阶段 1。

### 阶段 3：插件系统（规模：大）

- **做什么**：插件包与清单缓存、安装（请求、权限确认、复制到位）、清单 v2、版本绑定与升级、依赖与导出、JS 沙箱、宿主能力与权限检查、惰性激活与空闲回收、运行（进度、取消、历史、保留结果）、多语言查表。
- **原型里换成真的**：插件树、插件页、运行记录、任务面板、命令面板。
- **做完你能看到什么**：用一个示例插件（原型里 SQL 页的简化版，只做假执行）走通全程：安装、启用、打开它的页面、填参数、运行、看进度、看历史。
- **验收**：每种越权都被拒绝并有测试；1 万个清单时启动只读缓存；一个插件卡死或崩溃不影响别的；升级失败数据不动。
- **依赖**：阶段 1、2。

### 阶段 4：外壳补全（规模：中）

- **做什么**：把原型里没做的补上，并把界面规格定稿。
  - 大表格和大树的虚拟滚动。
  - 未保存内容被别处修改时的合并提示。
  - 类型自供的子节点（SQL 下的历史、综合节点）。
  - 多窗口、多工作区的新建、切换、删除。
  - 通知入口；导出、复制等现在只弹提示的功能。
  - `ui-spec.md` 里标着“默认，待确认”的 30 处逐条定下来。
- **做完你能看到什么**：外壳不再有“只弹提示”的按钮。
- **验收**：`ui-spec.md` 逐项对照；I.8 逐项对照 VS Code；浅色、深色截图。
- **依赖**：阶段 3。可以与阶段 5 交叉进行。

### 阶段 5：基础插件，第一个能日常使用的版本（规模：中）

- **做什么**：网址、笔记、提示词、HTTP 请求（按新接口重写）；语言插件（英、中、日）；综合；集合；欢迎页；本地插件市场。
- **做完你能看到什么**：可以真正开始用它记东西、存网址、发请求；能从一个本地文件夹安装插件；切换语言立即生效。
- **验收**：第一轮需求的验收项（按冲突清单修正后）全部通过。
- **依赖**：阶段 3、4。

### 阶段 6：sqlpool 的全部功能（规模：大）

- **先做**：单独设计“AI 接口”（给外部 AI 客户端用），你确认后再开发。
- **做什么**：数据源、SQL、查询目录、表、服务器命令、本机脚本、AI、AI 接口（MCP）；另有硬盘文件、API 连接。
- **做完你能看到什么**：日常用 sqlpool 做的事都能在 OneDesk 里做。
- **验收**：`sqlpool-parity.md` 的 90 项逐行通过；同一份查询在 sqlpool 和 OneDesk 里结果相同。发现内核缺东西就回内核补，不在插件里绕过。
- **依赖**：阶段 5。

### 阶段 7：版本化与同步的基础（规模：中）

- **做什么**：git 镜像（提交、推送、拉取、冲突处理、分支）；来自 git 的放宽需要本机确认。
- **验收**：需求 I.9 逐条对照。
- **依赖**：阶段 1。可以提前到阶段 6 之前，如果你更急着要它。

### 阶段 8：Vioros 的全部功能（规模：中）

- **做什么**：插件自带界面（界面模块直接加载）；视频库插件。
- **验收**：`vioros-parity.md` 的 56 项逐行通过；在 OneDesk 里上传的视频用 Vioros 原应用能播放，反之亦然。
- **依赖**：阶段 5。与阶段 6、7 没有先后关系。

### 阶段 9：远程（规模：大）

- **做什么**：网页访问正式版、无界面服务器、多设备同步、服务器插件市场、发布与订阅。
- **每一项都先单独设计**，你确认后再开发。
- **依赖**：阶段 7。

### 顺序与里程碑

```
1 内核 → 2 协议/接上原型 → 3 插件系统 → 4 外壳补全 ─┐
                                                    ├→ 5 基础插件 → 6 sqlpool ─┐
                                                    │               8 Vioros ──┼→ 9 远程
                                         7 版本化 ──┘（可提前）               ─┘
```

| 里程碑 | 在哪个阶段之后 | 意味着什么 |
|---|---|---|
| 内核可用 | 3 | 框架立住了：真数据、真插件、真权限 |
| 可以日常使用 | 5 | 第一个你能每天打开的版本 |
| 替代 sqlpool | 6 | 第一个验证条件达成 |
| 接入 Vioros | 8 | 第二个验证条件达成 |

## 5. 原型里的每个页面，谁来做、在第几阶段

原型里看到的页面分两类：一类是框架自带的，由外壳和内核做；一类是插件的页面，由对应的插件做。

| 原型里的东西 | 归谁 | 换成真的在哪个阶段 |
|---|---|---|
| 活动栏、标签栏、页面框架、状态栏、分割线 | 外壳 | 2（已有，接真数据） |
| 资源树、收藏、已删除 | 外壳 + 内核 | 2 |
| 环境树、环境页（含参数来源、继承图标、历史与恢复） | 外壳 + 内核 | 2 |
| 工作区配置树、配置页 | 外壳 + 内核 | 2 |
| 审计页 | 外壳 + 内核 | 2 |
| 信息面板（左侧） | 外壳 + 内核 | 2 |
| 搜索 | 外壳 + 内核 | 2 |
| 插件树、插件页 | 外壳 + 内核 | 3 |
| 运行记录树、运行记录页、任务面板 | 外壳 + 内核 | 3 |
| 命令面板 | 外壳 + 内核 | 3 |
| 结果区（结果、历史页签；导出、复制） | 外壳 + 内核 | 3，导出在 4 |
| 笔记页 | 笔记插件 | 5 |
| SQL 页（参数区、编辑区、运行、最终 SQL） | SQL 插件 | 6（阶段 3 先用简化版当示例） |
| 数据源树、数据源页 | 数据源插件 | 6 |
| 文件树 | 硬盘文件插件 | 6 |
| 结果区的“AI 分析”页签 | AI 插件 | 6 |

原型里没有、但要开发的页面：网址、提示词、HTTP 请求、综合、集合、欢迎页、本地插件市场（阶段 5）；查询目录、表、服务器命令、本机脚本（阶段 6）；视频库（阶段 8）。它们用的是同一套页面框架，不需要再做一轮原型；其中视频库的页面由插件自己画，开发前我会先给你看草图。

## 6. 每个阶段固定要做的事

1. 开始前：写清这个阶段的接口和任务，范围外的问题记入 `docs/handoff/todo.md`。
2. 过程中：改完就编译、就跑对应的测试；小步提交。
3. 结束时：`pnpm check` 全过；真实启动应用把主要流程点一遍；没运行过、没看到结果的如实写出来。
4. 结束时：写交接文件；新的决定记入 `decisions.md`；更新 `CLAUDE.md` 里过时的部分。
5. 结束时：把能看到的东西给你看，你确认后进入下一个阶段。

内核（阶段 1–3）由主会话自己写，不拆给多个会话并行，因为各部分互相咬合。插件（阶段 5、6、8）之间互不依赖，可以并行。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 原型的协议与内核设计对不上 | 阶段 2 返工 | 阶段 2 一开始就对齐，以 Rust 为准 |
| 桌面窗口里编辑器、日期控件表现不同 | 阶段 2 要调整界面 | 阶段 2 第一件事就是在桌面窗口里跑 |
| 多个插件版本并存的规则复杂 | 阶段 3 容易出错 | 按内核设计 7.6 的表逐条写测试 |
| “AI 接口”还没有设计 | 阶段 6 无法开始 MCP 部分 | 阶段 6 开头先设计，其余插件不受影响 |
| 历史存整条快照占空间 | 长期使用后库变大 | 阶段 1 实测；必要时加清理规则 |
| 延迟数字是在高负载下测的 | 判断可能偏乐观或偏悲观 | 阶段 2 在空闲机器上重测 |

## 8. 需要你确认的

1. 阶段的顺序，特别是阶段 7（git）是否要提前。
2. 每个阶段结束时停下来给你看，确认后再继续——还是连续做下去，只在里程碑处停。
