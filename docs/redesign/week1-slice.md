# 本周目标：最小可展示版本

状态：待确认。
依据：`dev-plan.md`（完整计划不变）、`kernel-design.md`、界面原型 `prototype-v1`。
背景：本周额度只剩一半左右，完整做完阶段 1–3 不现实。所以本周不按阶段整块做，而是从阶段 1、2、3、5 里各取最少的一部分，贯通成一个真的、能展示的系统。

## 1. 做完是什么样

打开桌面应用（真窗口，不是浏览器里的假数据）：

1. 左边的资源树是真的：能新建分组、新建笔记、改名、拖动、删除，重启后都还在。
2. 指定一个本机文件夹，文件树里列出其中的文件和子文件夹。
3. 点一个文本文件，在标签页里打开；编辑、保存；标签上有未保存标记；关闭前询问。
4. 界面就是原型的样子。
5. 这两种页面（笔记、文本文件）各由一个真正的插件提供，插件运行在沙箱里，只能通过宿主接口读写。

## 2. 范围

**做**

| 部分 | 内容 | 取自 |
|---|---|---|
| 内核 | 工作区文件夹与数据库；统一写入管线（事务、历史、审计都写，但只做“写入”，查看和恢复界面不做）；资源与存储树（新建、改、移动、删除）；提供树 | 阶段 1 |
| 进程与协议 | 主进程 + 一个工作进程；请求/应答与事件；Rust 类型生成 TS 类型；原型的协议对齐到 Rust | 阶段 2 |
| 插件系统 | 读清单（v2 的子集）；JS 沙箱；宿主能力只做三样：`resources`、`files`（授权文件夹内读、写、列目录）、`ui`；页面渲染与字段绑定、保存 | 阶段 3 |
| 外壳 | 原型接真数据：资源树、文件树、标签页、页面框架、信息面板；在桌面窗口里跑通 | 阶段 2 |
| 插件 | 笔记；文本文件（文件树 + 文本编辑页） | 阶段 5、6 的一小部分 |

**本周不做**（原型里这些地方继续显示假数据，并标明“演示数据”）

环境与参数、策略、搜索、收藏、已删除树、导出导入、运行与结果区、任务面板、插件安装与市场、版本绑定与升级、多语言插件、多工作区、审计和历史的查看界面、git、其余全部插件。

本周做的每一块都按内核设计来写，是完整计划里对应部分的开头，不是另写一套临时代码。下周接着往上加，不返工。

## 3. 分工

先由协调会话定好协议（内核对外的方法和类型），之后三块并行，各自一个会话、一个分支：

| 会话 | 任务 | 建议的模型 | 说明 |
|---|---|---|---|
| 协调 | 定协议；拆任务；审查；合并；最后真实运行验收 | Fable | 新开一个会话来做，见第 4 节 |
| 内核 | Rust 内核库 + 工作进程 + 沙箱与三样宿主能力 | Opus | 最要紧的一块，按 `kernel-design.md` §3–§5、§7.4–7.5 |
| 外壳 | 主进程（Tauri）；原型接真协议；桌面窗口里跑通 | Sonnet | 界面已有，主要是接线 |
| 插件与测试 | 笔记插件、文本文件插件；界面检查改为连真内核 | Sonnet | 依赖前两块的接口，接口定了就能写 |
| 审查 | 只看代码和设计，不看实现者的推理 | Opus | 合并前一次 |

规则沿用 requirements.md F 节：一个文件同一时间只有一个写入者；会话之间只通过 `docs/handoff/` 交流；接口由协调会话定。

## 4. 为什么新开会话

当前这个会话的上下文已经用了六成，里面大部分是设计讨论的过程。之后每做一步都要带着这些内容，既贵又容易在压缩时丢细节。设计的结论已经全部写进文件（设计、两份验收条件、开发计划书、本文件），新会话读文件就能接上，不需要这段对话。

所以：协调工作交给一个新会话，它的第一件事是读 `CLAUDE.md`、`kernel-design.md`、`dev-plan.md` 和本文件。

## 5. 额度的估计（不是承诺）

- 第一版（整个应用，55 个提交）用了周额度的六分之一。
- 今天用得多，主要花在长对话反复带着上下文，以及三个并行助手上，不是花在写代码上。
- 本周这个范围比第一版小，但内核是用 Rust 新写的。按第一版的花费推算，大约需要周额度的六分之一到四分之一。这个估计没有依据可核对，可能偏差较大。
- 控制花费的办法：新会话、上下文保持短；内核以外的部分用较小的模型；不做范围之外的事。
- 如果做到一半额度不够，按这个顺序保：内核与协议 → 资源树接真数据 → 笔记插件 → 文本文件插件。前三样做完就已经是一个真的、能展示的系统。

## 6. 验收

3. 文本文件插件访问授权文件夹之外的路径被拒绝（有测试）。
4. 内核测试、类型检查、界面规范检查通过。
