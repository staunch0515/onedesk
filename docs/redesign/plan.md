# OneDesk 重新开发：规划

状态：待确认。依据：`docs/requirements.md`（A–I 全部）、`docs/decisions.md`（D01–D207）、`docs/design/` 下的草案、现有代码（main，55 个提交）。
配套文件：`docs/redesign/kernel-design.md`（设计，批准后才开发）。

## 1. 结论

1. 第一版做成了“菜单 + 单页表单”的资源管理工具。第二轮需求要的是一个**工作台**：树、标签页、结果区、环境参数、历史、权限、审计、工作区，全部是内核机制，具体功能全部由插件提供。两者的骨架不同，所以不是在第一版上补功能，而是内核重写。
2. 内核从“网页里的 TypeScript”改为“独立进程里的 Rust”，插件在沙箱里运行。原因在第 5 节；这是本次最大的一个决定。
3. 设计系统（token、基础组件）保留。Rust 的数据库、迁移、快照、钥匙串代码大部分保留。TypeScript 内核、外壳页面、四个插件按新接口重做。
4. 分九个阶段。先内核，再协议，再插件系统，再外壳，再用复杂插件（SQL、硬盘文件、Vioros）检验框架。每个阶段可运行、有测试。

## 2. 我对需求的理解

一句话：OneDesk 是一个像 VS Code 一样布局的工作台，用来逐步替代日常软件；内核只提供通用机制，任何具体功能都是插件。

需求（I.0c）点名内核只保留七种机制，另外有四项贯穿全局的要求。逐项对照第一版：

| 机制 | 需求要什么 | 第一版 |
|---|---|---|
| 资源 | 统一条目；记录创建者和编辑者的插件版本；来自外部目录的资源以文件为源头 | 有，但分组只是一个字符串，没有操作者记录 |
| 插件 | 稳定 id + 发布版 id，多版本共存、固定、回退；依赖带版本范围；上万个插件时只读清单、用时才激活；只能用宿主给的能力 | 有，但与宿主同进程（可绕过权限），能力在激活时才登记（无法惰性加载），没有版本和依赖 |
| 树 | 资源树、环境树、配置树、插件树、数据源树、文件树；无限嵌套；插件可以提供新的树；拖拽和右键由插件决定 | 没有，只有一层菜单 |
| 标签页 | 一切在标签页中打开；每个标签页有自己的环境；可固定、记住 | 没有，单页 |
| 参数 | 环境树和配置树同一套机制：类型化参数、父子继承、覆盖；保护类参数只能加严；占位符由插件定义，内核只负责取值 | 没有 |
| 历史 | 修改历史（谁、何时、改前改后、可恢复）；执行历史（每个资源 200 次，可复用参数） | 没有 |
| 权限 | 网络白名单、密钥、文件授权文件夹、外部程序；环境可以进一步收紧 | 只有网络和密钥名单，且可绕过 |
| 结果区 | 每个标签页下方；按输出类型显示；失败原因留住；可交给 AI | 只有一行状态 |
| 工作区 | 一个工作区一个数据库文件、一个进程；彻底隔离；设置只属于工作区 | 没有，单库 |
| 审计 | 每个工作区一份，只追加 | 没有 |
| 多语言 | 语言是插件；默认英语；功能插件自带文字 | 中文写死 |

还有一组“以后做，但现在不能堵死”的要求：git 版本化、网页访问、家庭服务器、发布与订阅、AI 接口、多设备同步。

## 3. 第一版不完整的根本原因

1. **把“视图”理解成了页面里的一块内容**，而需求里的界面骨架（树、标签页、结果区）本身就是内核机制和插件的扩展点。
2. **内核放在网页里**。网页访问、无界面服务器、审计不可绕过、后台任务，都要求内核在界面之外。
3. **插件的能力在代码里登记**。要支持上万个插件和按需激活，能力必须写在清单里，代码只提供行为。
4. **没有统一的写入入口**。历史、审计、权限、版本化都要求“每一次修改经过同一个地方”。

## 4. 需求里互相矛盾或没说清的地方

需求是分多次补充的，后面的常常推翻前面的。下面是我找到的全部冲突和我的处理。原则：后来的优先；两条都合理时，选机制更少的那种。

| # | 冲突 | 处理 |
|---|---|---|
| 1 | A 节资源有 `group` 字段；I.3 要无限嵌套的树，不设“未分组” | 取消 `group` 字段。分组本身是一个节点，资源记录父节点和顺序 |
| 2 | D.3“停用插件后菜单项消失”；B 节和 ui-spec“灰色显示，不隐藏” | 树里灰色显示（隐藏会让分组结构残缺）。D.3 的验收改为“变灰、不可运行、数据保留” |
| 3 | “视图树只有四种节点”“插件不含界面代码”；D206“节点可扩展”“插件可提供标签页类型（如播放器）” | 基础节点仍是四种。插件要自带界面时，放在隔离的框架（iframe）里，只通过消息与宿主通信。自定义节点和自定义标签页是同一个机制 |
| 4 | D02“插件视图里的表单只读”；SQL 页面要编辑 SQL 和参数 | 表单字段可以绑定到资源的字段，由框架统一管理草稿、未保存标记和保存 |
| 5 | I.9“历史、恢复、对比都基于 git 提交”；I.4 环境的历史和恢复必须有，而 git 是可选的 | 修改历史始终保存在工作区数据库里。开启 git 后，每条历史对应一次提交；git 是镜像和同步手段，不是历史的唯一来源 |
| 6 | D176 文件能力“不提供写入和删除”；D183 要完整的文件管理 | 以 D183 为准 |
| 7 | sql-plugin.md“命令与 SQL 同一个插件”“参数改为绑定”；D185“命令是单独插件”、D177“沿用字面量替换” | 以 D185、D177 为准，草案相应改掉 |
| 8 | I.11“数据库类插件不在里程碑二”；D185、D207 更正“SQL、数据源都要加进来验证框架” | 以 D207 为准 |
| 9 | ui-spec“没有工作区时进欢迎页”；I.10“首次使用时只有一个工作区”；D196“欢迎页是插件”（没有工作区就没有已启用的插件） | 首次启动自动建一个默认工作区，再在其中打开欢迎页 |
| 10 | D178“一个工作区一个进程”；I.10“应用只有一份” | 一个应用，每个打开的工作区一个内核进程（见设计 §2） |
| 11 | D60“插件不能把动作或视图挂到别的插件的类型上”；I.0e“依赖方直接挂到对方的树上，使用它的标签页和结果区” | 以 I.0e 为准：对方在清单里声明“导出”的扩展点，依赖方才能用 |
| 12 | CLAUDE.md“内核抛中文错误”“文案放 zh-CN.ts”；I.1“语言是插件，默认英语，文字不写死” | 内核只返回错误码和参数；文字全部来自语言文件 |
| 13 | I.13 审计“不修改、不删除”；同节“用户可以导出后清理（待确认）” | 第一版不提供清理。以后要做时，清理本身作为一条审计记录 |
| 14 | D58 把插件隔离推到“下一阶段” | 现在做。权限、审计都以隔离为前提 |
| 15 | 数据源要连 PostgreSQL；内核不得认识具体功能 | 内核不内置数据库驱动。提供通用能力“运行清单里声明的外部程序”（Vioros 的 yt-dlp 同一机制），数据源插件自带连接程序 |

I.12 列出的“待设计”项（同步文件夹、环境保护的界面、家庭服务器的安装等）不在本次设计内，各自在对应阶段开始前单独设计。

## 5. 总体方针

**内核是一个独立的 Rust 进程，一个工作区一个；界面是它的客户端；插件在沙箱里。**

理由，每条都对应一条需求：

- I.10c 网页访问、I.10d 无界面服务器：“功能都在这台电脑上执行，网页只负责显示和操作”。内核在网页里就做不到。
- I.13 审计只追加、权限不可绕过（D58 的遗留）：检查必须在插件够不着的地方做。
- I.5 慢操作放后台、调用来源有“定时”和“AI”：没有窗口时内核也要能运行。
- D178 一个工作区一个进程：内核进程按工作区启动，天然满足，也天然隔离。
- 测试：界面测试可以用真实浏览器连真实内核，不再需要 sql.js 的“预览模式”（临时措施 T01 随之消失）。

代价：TypeScript 内核约 2,700 行（含测试约 5,000 行）要用 Rust 重写；插件沙箱引入一个 JS 引擎依赖（需先做技术验证）。

不这样做的另一条路是保留网页内核、逐步加功能。它无法满足网页访问、无界面、审计和权限这四项，迟早还要再重写一次，所以不建议。

## 6. 阶段

每个阶段结束时：`pnpm check` 全过，真实启动点一遍，写交接文件，新决定记入 decisions.md。

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| 0 准备 | 第二轮需求文档入库；三项技术验证：JS 沙箱（异步、模块、超时中断、内存上限）、内核进程与界面的通信、Rust 类型生成 TS 类型 | 每项有可运行的小样和结论；失败的换备选方案并记录 |
| 1 内核基础 | 工作区与应用级存储、迁移（含旧库升级）、统一写入管线（操作者、事务、历史、审计、事件）、资源与树、参数与环境、策略（只能加严）、搜索、引用、收藏、密钥、导出导入、快照 | Rust 测试覆盖率 ≥ 80%；1 万条搜索 < 200 ms；旧库升级不丢数据 |
| 2 协议与进程 | 内核进程、请求/事件协议、桌面端转发、本机 WebSocket（开发与测试用）、TS 客户端 | 浏览器和桌面窗口连同一个内核，行为一致；协议有契约测试 |
| 3 插件系统 | 插件包与索引、清单 v2、版本/固定/回退、依赖与导出、沙箱运行时、宿主能力与权限检查、惰性激活、运行（进度、取消、历史 200 次）、多语言解析 | 每种越权都有被拒绝的测试；1 万个清单启动只建索引；激活失败不影响其他插件 |
| 4 工作台外壳 | 活动栏、树、标签栏、页面（标题、操作区、内容、结果区）、状态栏、搜索与命令面板、分割线；环境页、配置页、插件页、审计页；视图树渲染；沿用设计系统 | ui-spec.md 逐项对照；I.8 逐项对照 VS Code；浅色、深色截图 |
| 5 基础插件 | 网址、笔记、提示词、HTTP 请求（按新接口重写）、语言（英、中、日）、综合、欢迎页 | 原验收 D.1–D.6（按 §4 修正后）全部通过；切换语言立即生效 |
| 6 复杂插件 | 硬盘文件（文件树、授权文件夹）、数据源、SQL、命令、API 连接、AI 接口 | 逐项对照 sql-plugin.md 的功能表；框架缺口逐条记录并回到内核修，不在插件里绕过 |
| 7 版本化与工作区 | git 镜像（提交、推送、拉取、冲突、分支）、工作区模板、新建/复制/删除、多窗口 | I.9、I.10 逐条对照 |
| 8 界面扩展与 Vioros | 插件自带界面（隔离框架）、外部程序下载与校验、Vioros 插件 | D189 的功能清单逐项对照 |
| 9 远程 | 网页访问正式版（口令、加密、局域网）、无界面服务器、同步、发布订阅 | 各自先单独设计，再开发 |

顺序的理由：1 → 2 → 3 是内核，后面一切依赖它。4 需要 2 才能开始，可以与 3 并行。5 是第一次端到端验收。6 用最复杂的插件压框架，越早暴露缺口越好，所以排在 7、8 之前。

本次请你批准的设计覆盖阶段 0–3（内核）以及 4–8 的接口形状。外壳的界面规格已有草案（ui-spec.md），各插件的设计在各自阶段开始时补齐并确认。

## 8. 工作方式

沿用 requirements.md E、F、G、H 节：主会话定接口和合并；模块各自分支；先检查后提交；真实运行后才说完成；范围外的问题记 todo。内核（阶段 1–3）由主会话自己写，不拆给多个会话并行，因为它的各部分互相咬合，拆开容易走样。

## 9. 需要你确认的事

设计文件 §14 列出了全部待批准的决定。其中三条影响最大：

1. 内核改为独立的 Rust 进程，插件在 JS 沙箱里运行。
2. 修改历史始终存在数据库里，git 只做镜像（§4 第 5 条）。
3. 数据库连接等能力通过“插件自带外部程序”实现，内核不内置驱动（§4 第 15 条）。
