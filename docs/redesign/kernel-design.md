# OneDesk 内核设计

状态：待批准（第 3 稿，已按两轮复查修订）。批准前不写代码。
依据：`docs/requirements.md`、`docs/decisions.md`（D01–D207）、`docs/redesign/plan.md`。
验收：`docs/redesign/sqlpool-parity.md`、`docs/redesign/vioros-parity.md`（sqlpool 和 Vioros 的全部功能必须能用插件做出来）。
范围：整体结构、内核（数据、写入、资源与树、参数、插件、运行、页面、搜索、协议）和插件接口的形状。外壳界面见 `docs/design/ui-spec.md`；各插件的设计在各自阶段补齐。

## 1. 设计原则

1. **内核不认识任何具体功能**。内核里只有机制：资源、树、参数、插件、运行、历史、权限、审计、页面。
2. **一个概念一种机制**（I.0c）。本设计中的合并：
   - 分组、环境、配置项、插件状态都是资源，共用同一套树、历史、搜索。
   - 环境、工作区配置、插件设置共用同一套参数。
   - 动作执行、后台任务、导入、同步共用同一套“运行”。
   - 自定义视图节点和自定义标签页共用同一套“隔离界面”。
3. **每一次修改只有一个入口**。权限检查、历史、审计、事件在这个入口里一次完成，任何调用方都绕不过去。
4. **能力写在清单里，行为写在代码里**。内核只读清单就知道一个插件提供什么、需要什么。
5. **拒绝优先**。权限判断拿不准时拒绝；缺少判断依据（例如没有环境）时按最严处理；每一种拒绝都有测试（H 节）。
6. **文件夹即事实**。有哪些工作区、有哪些插件，以文件夹里实际有什么为准，不另设登记处。

## 2. 进程与分层

采用主进程-工作进程模式（与 Chrome、VS Code 相同），只有一个工作区时合并为单进程（2.5）。下图是多进程时的三种角色，职责不重叠：

```
┌─ 主进程（一个，Tauri）─────────────────────────────────────────┐
│ 应用生命周期 · 窗口的创建与销毁（托盘、全局快捷键预留）         │
│ 工作进程的启动、监视、重启、关闭 · 消息转发                     │
│ 工作区文件夹和插件文件夹的唯一管理者（新建、删除、安装、移除） │
│ 网页访问的唯一入口（开启时）                                    │
└───┬───────────────┬──────────────────────┬────────────────────┘
    │ 窗口 A         │ 窗口 B               │ 本机套接字（每个工作进程一条）
┌───▼────┐      ┌───▼────┐          ┌──────▼───────┐  ┌──────────────┐
│ 界面    │      │ 界面    │          │ 工作进程      │  │ 工作进程      │
│ React  │      │ React  │          │ 工作区“个人” │  │ 工作区“甲公司”│
└────────┘      └────────┘          │ 内核库        │  │ 内核库        │
  只画界面，只经协议工作             │ 插件沙箱 × N  │  │ 插件沙箱 × N  │
                                    └──────────────┘  └──────────────┘
```

### 2.1 主进程

只做调度，不含任何业务逻辑，不打开任何工作区数据库。它需要知道的关于工作区的少量信息（名称、上次打开时间、窗口位置）放在每个工作区文件夹里的 `workspace.json` 中（3.1）。

- **生命周期**：单实例（第二次启动只是把已有应用提到前面）；退出时先通知所有工作进程收尾，再退出。
- **窗口**：创建、销毁、记住位置和大小；一个窗口同一时间只属于一个工作区（I.10）。
- **托盘图标、全局快捷键**：位置预留在主进程，首期不做，也不引入相关依赖。
- **工作进程管理**：按工作区启动；监视；崩溃后自动重启并在窗口里说明（规则见 2.4）；最后一个窗口关闭后关闭它。
- **转发**：界面的请求按窗口所属的工作区转给对应的工作进程，事件原路推回。主进程不解释内容，只在连接上标明操作者和客户端标识。
- **文件夹管理**：新建或删除工作区文件夹、安装或移除插件包、维护插件清单缓存，只由主进程做。工作进程对这些文件夹只读，要改时向主进程发请求。这样跨进程没有写冲突。
- **需要工作区内部数据的事由工作进程做**：新建工作区时复制配置，由主进程请当前工作进程导出配置、请新工作进程导入；这些操作的审计由相关的工作进程写在自己的库里。
- **网页访问**：开启后由主进程监听端口、校验口令，再按工作区转给工作进程。工作进程自己从不监听网络。是否开启、端口等是工作区配置里的参数，主进程启动工作进程后向它读取；口令在钥匙串。

### 2.2 工作进程

每个打开的工作区一个，专心处理该工作区的业务（D178）。

- 内容：内核库 + 该工作区的数据库文件 + 每个已激活的插件版本一个 JS 沙箱。
- 只与主进程通信。不认识窗口，不知道请求来自桌面窗口还是浏览器。
- 一个工作区同一时间只被一个工作进程打开。用操作系统的文件锁实现，进程一退出锁自动释放，不会因为崩溃留下假锁。同一工作区开第二个窗口时，两个窗口连同一个工作进程。
- 主进程消失（崩溃或被强杀）时，工作进程发现连接断开，完成当前事务后自行退出。它启动的外部程序在同一个进程组里，随它一起结束，不留孤儿进程。
- 工作进程崩溃只影响它自己的工作区；数据库用事务和预写日志，重启后数据完整。

### 2.3 界面

每个窗口一个，只通过协议客户端工作。桌面窗口经主进程转发；浏览器经 WebSocket 连主进程。界面代码是同一套（I.10c）。

### 2.4 几种情形

| 情形 | 发生什么 |
|---|---|
| 在当前窗口打开另一个工作区 | 主进程把这个窗口改连目标工作区的工作进程（没有就启动）；原工作区若已无窗口，其工作进程关闭 |
| 新窗口打开工作区 | 主进程新建窗口并连到该工作区的工作进程，两个工作区并行（I.10） |
| 无界面服务器（I.10d） | 主进程以无窗口方式运行，按启动参数指定的工作区启动工作进程，只提供网页访问；结构与桌面版相同 |
| 关闭某工作区的最后一个窗口，而它有运行未结束 | 提示有运行未结束，由用户选择等待或取消（托盘做了之后可改为后台继续） |
| 工作进程崩溃后重启 | 遗留的“运行中”记录改为失败并写明原因；界面重新订阅并整体刷新；不自动恢复崩溃时正在激活的插件的标签页，而是提示“上次在某插件处中断”，由用户决定是否打开或停用它；连续崩溃时重启间隔逐次加长 |

### 2.5 运行模式：单进程或多进程

多进程对只用一个工作区的人没有好处，所以有两种模式，由工作区的数量自动决定。两种模式下内核库、协议、界面完全相同，区别只在“工作进程的内容放在哪里”。

| | 单进程 | 多进程 |
|---|---|---|
| 结构 | 内核库直接运行在主进程里，没有工作进程 | 2.1–2.4 所述：主进程 + 每个工作区一个工作进程 |
| 同时打开的工作区 | 一个 | 多个，各自一个窗口 |
| 切换工作区 | 可以：在当前窗口关闭当前工作区（有未结束的运行时先询问），再打开另一个 | 可以：当前窗口切换，或新窗口并行 |
| 插件或内核崩溃 | 整个应用退出，重启后数据完整 | 只影响该工作区，自动重启 |
| 网页访问、无界面服务器 | 支持 | 支持 |
| 启动 | 少一次进程启动和连接 | 多一次 |

规则（没有开关，也没有要保存的设置）：

- 启动时数 `workspaces/` 下有几个工作区文件夹（以其中有 `workspace.db` 为准）：一个就是单进程；两个或更多就是多进程。
- 运行中新建了第二个工作区：界面提示“重新启动后才能两个窗口并行”，并提供“现在重新启动”。不重启时仍可在当前窗口切换过去。
- 删到只剩一个工作区：下次启动回到单进程。
- D178（一个工作区一个进程）在两种模式下都成立：单进程模式下，这一个进程只承载一个工作区。

实现上，主进程通过同一个接口与内核交谈，接口有两种实现：进程内直接调用，或经本机套接字连工作进程。消息格式相同（进程内也按协议的消息收发），所以两种模式的行为由同一组协议测试保证一致。

这个做法的代价见 §17。

### 2.6 代码划分

- `onedesk-kernel`（Rust 库，不依赖 Tauri）：全部内核逻辑。
- `onedesk-worker`（可执行文件）：为一个工作区运行内核库，对主进程提供协议。只在多进程模式下使用。
- `onedesk`（Tauri 应用，主进程）：2.1 的内容；单进程模式下同时承载内核库。
- 界面（React）：协议客户端、外壳、设计系统。

依赖方向：`界面 → 协议 → 主进程（转发）→ 工作进程（单进程模式下省去）→ 内核库 → 插件沙箱`。内核库不得出现任何插件的 id、类型名或逻辑（`pnpm lint` 检查，延续现有规则）。

## 3. 数据

### 3.1 目录

```
~/Library/Application Support/onedesk/
  plugins/<插件id>/<版本>/      插件包（多版本并存，所有工作区共用，I.10）
  plugins/.index               插件清单的缓存，可随时删除，会自动重建
  workspaces/<文件夹名>/
    workspace.json             工作区 id、显示名称、上次打开时间、窗口位置
    workspace.db               该工作区的全部数据
    blobs/                     大的运行结果、附件
    plugin-data/<插件id>/      插件自己的目录：它的程序、临时文件、缓存
    backups/                   启动快照，保留 7 份
```

没有单独的“应用数据库”。有哪些工作区，看 `workspaces/` 下有几个含 `workspace.db` 的文件夹。启动时打开上次打开时间最近的那个。第一次启动时一个都没有，就自动建一个默认工作区。

`workspace.json` 是一个很小的文本文件，让主进程不用打开数据库就能列出工作区。它丢了或坏了不影响数据：名称退回文件夹名，id 从数据库里读回。

工作区 id 是创建时随机生成的，存在 `workspace.json` 和数据库里，不随文件夹改名而变，也不会被以后的工作区重用。钥匙串按这个 id 分账户。由此：

- 文件夹可以随意改名，密钥不受影响。
- 删掉一个工作区文件夹后再新建，新工作区拿不到旧工作区留在钥匙串里的密钥。通过应用删除工作区时，它在钥匙串里的条目一并删除。
- 手动复制一个工作区文件夹：只应在该工作区关闭时进行。启动时发现两个文件夹 id 相同，后发现的那个被赋予新 id，成为独立的工作区，密钥需要重新填写。

新建工作区：建一个新文件夹和空数据库，把当前工作区的配置树（外观、语言等）和插件启用状态复制过去；数据不复制。复制是一次性的，之后互不影响。

现有的 `onedesk.db` 在第一次启动新版本时移到 `workspaces/default/workspace.db`，再按迁移文件升级（规则 6：只新增迁移，旧库升级有测试）。旧库里的类型名是短名（如 `link`）。迁移不改它们，因为内核不能认识具体插件；由插件在清单里声明“我接管旧类型名 link”，在启用时认领并改成新写法。

### 3.2 工作区数据库的表

| 表 | 内容 | 说明 |
|---|---|---|
| `resources` | 所有节点：资源、分组、环境、配置项、插件状态 | 见 3.3 |
| `revisions` | 每次修改一行：资源、序号、时间、操作者、操作、改了哪些字段、改后整条记录的快照、对应的 git 提交 | 修改历史与恢复的唯一来源。默认全部保留 |
| `audit` | 审计记录，只追加 | 数据库触发器禁止修改和删除 |
| `runs`、`run_artifacts` | 运行记录及其附属内容（如 AI 分析） | 每个资源保留最近 200 次；没有资源的运行按动作保留 200 次；“保存结果”的不清理 |
| `refs` | 资源之间的引用 | 与资源在同一事务里更新 |
| `param_decls` | 每个资源声明了哪些参数 | 环境页据此自动列出参数（I.4“不需要手动增删”）；可随时重建 |
| `resource_meta` | 收藏、最近使用时间、使用次数 | 属于本机，不进入版本化 |
| `plugin_storage` | 插件自己的键值存储 | 按插件、按版本隔离（7.6） |
| `ui_state` | 标签页、布局、展开状态、列宽 | 界面状态，不版本化、不同步（I.0b）；按客户端分开存（9.2） |
| `secret_names` | 密钥名字 | 值只在钥匙串，账户名为 `<工作区id>/<名字>` |
| `outbox` | 待处理的后续工作（待提交到 git 的修改、待重建的参数声明） | 重启后不丢 |
| `meta` | 结构版本、工作区 id | |

### 3.3 资源

```
id             稳定 id
kind           类型，写成 “插件id:类型名”（如 org.onedesk.link:link）；内核自带的写成 core:group 等
plugin_version 这条资源绑定的插件版本，由该版本处理（见 7.6）
tree           所在的树
parent_id      父节点；空表示在树的根下
pos            同级中的顺序
name, description, tags, body(JSON)
visibility, ai_visible, origin(original/subscribed/copied), origin_ref
external_key   外部来源的唯一键（如文件路径）；同一类型内唯一，用于“重复导入只更新”
state          ok / missing（源头不存在）/ conflict（有冲突，只读）
rev            修改序号
created_at, created_by, updated_at, updated_by     操作者见 4.1
deleted_at     删除标记，见 3.4
```

与第一版的差别：`group` 字符串改为 `tree + parent_id + pos`；类型名带插件 id（上万个插件时不撞名，I.6）；增加版本绑定、操作者、外部键、状态、删除标记。

内核自带四种类型，它们是机制，不是功能：

- `core:group`：分组，只有名字，可以放任何节点。
- `core:env`：环境节点，body 是参数表。
- `core:config`：配置节点，body 是参数表。
- `core:plugin-state`：某个插件在本工作区的状态（启用、启用哪个版本、设置、授权），body 是参数表。它们放在一棵不直接显示的存储树里；插件树显示时把它与插件文件夹的内容合在一起。这类节点是本机的决定，**不进入 git 版本化和同步**（见 §13）。

### 3.4 删除与恢复

- 普通删除只做标记：从树和搜索里消失，历史保留。已删除的资源在内核自带的“已删除”树里可以看到并恢复。
- 删除一个分组，连同它下面的全部节点作为一批一起标记；恢复时整批一起恢复。恢复时原来的父节点已不存在的，放到所在树的根下。
- 同一外部键再次导入时恢复原记录，不新建。
- **永久删除**：从“已删除”树里对一条资源执行，需要确认并说明不可撤销。它清除该资源的记录、全部历史快照和运行记录，只在审计里留一行“已永久删除”（不含内容）。用于清除误存的敏感内容。

### 3.5 导出与导入

- 导出工作区：一个文件夹，里面是可直接阅读的 JSON（资源、历史、运行记录、审计）和 `blobs/`；不含密钥的值，不含界面状态（G.2、I.13）。
- 导入到一个工作区，内容作为**新数据**（I.10，取代 G.2 的“相同 id 询问覆盖或跳过”）：每条资源得到新 id，资源之间的引用按新旧 id 的对应关系改写；带外部键且本工作区已有同一外部键的，更新已有那条，不新建；绑定的插件版本本机处理不了的不导入并列出（7.6）。
- 导入方不继承来源的历史和审计：导入的资源从一条“导入”历史开始；来源的审计只留在导出文件里供阅读，不写进本工作区的审计表。整次导入在本工作区的审计里记一行。
- 把一个工作区恢复到过去某个时刻是另一件事，用 `backups/` 里的快照，不走导入。

## 4. 写入管线

所有修改——来自界面、插件、导入、git 拉取、AI——都变成一条**命令**，交给同一个入口：

```
execute(调用上下文, 命令)
  1. 确定操作者
  2. 权限：调用方有没有这项能力；策略允不允许（6.3）
  3. 准备：需要插件参与的计算（校验 validate、升级 migrate）在这里先算好
  4. 一个数据库事务内：核对并发 → 写数据、搜索文本、引用 → 写 revisions → 写 audit → 写 outbox
  5. 提交后：发事件；按 outbox 重建参数声明、提交 git
```

要点：

- **事务里不调用插件**。插件的 `validate`、`migrate`、`parameters` 是纯计算：只接收数据、返回结果，执行期间不能调用任何会写入的宿主接口。它们在第 3 步或第 5 步运行，事务里只有内核自己的数据写入。这样插件卡住不会卡住整个工作区的写入，也不会出现“插件在别人的事务里再发起写入”。
- **提交按字段**：命令描述的是“改哪个字段”，不是“把整条记录换掉”。例如改一个环境参数是 `params.set(节点, 名字, 值)`。字段的粒度是：顶层字段、body 的第一层键、参数表里的每个参数。
- **并发规则**：命令带着它依据的序号 `rev`。只有“这次要改的字段，在那个序号之后被别人改过”才算冲突并被拒绝；改的是不同字段则两边都生效。
- **没有变化就不记**：命令执行后每个字段都与原来相同的，不产生历史，也不产生审计行（重复导入一万个没变的文件不会留下一万条记录）。
- **批量命令**：导入、整批删除、插件升级接管是一条批量命令，一个事务，要么全成要么全不成。每条资源各有一条历史，审计里是一行汇总。
- **派生数据**：搜索文本和引用由内核自己算，在同一事务里写，不会与数据不一致。参数声明需要问插件，所以放进 `outbox`，提交后重建；它丢了可以随时全量重建。
- 写入由一个专用线程串行执行；读取用独立的只读连接，不被写入阻塞。

### 4.1 操作者

```
{ type: user | core | plugin | ai | git | sync,
  id:   插件为发布版 id（org.x.sql@1.2.0）,
  source: manual | scheduled | ai }
```

对应 I.6（createdBy、updatedBy、调用来源）和 I.13（审计的操作者）。

### 4.2 历史与恢复

- 保存按整条记录：每条命令在 `revisions` 留下改后整条记录的快照，以及这次改了哪些字段。
- 显示按字段：把相邻两份快照比较，得出每个字段的改前值和改后值（I.4）。
- 恢复 = 直接取那一份快照，作为一条新的命令写回去，所以恢复本身也在历史里（I.4）。不靠一步步倒推。恢复出来的快照若绑定着别的插件版本，按 7.6 处理。
- 代价是占空间，尚未实测。如果某类资源很大又改得很勤，以后加“旧历史隔一段时间只留一份”的清理规则。
- 父环境改了某个参数后子环境标“已变化”（I.4）：子环境覆盖一个参数时，记下它当时继承到的值和这个值来自哪个节点；以后按当前的父链重新解析一次继承值，与记下的不同即为“已变化”。这样父节点改了别的参数不会误标，换了父节点也能正确判断。
- 开启 git 后（阶段 7）：版本化模块读 `outbox`，把纳入版本化的类型写成文件并提交，提交号写回 `revisions`。仓库里的外部改动作为操作者为 `git` 的命令进入同一条管线（D203）；两边都改过则把资源标为 `conflict`。git 不可用时 `outbox` 积压，恢复后补提交（I.9）。来自 git 的改动受 §13“放宽需确认”的限制。

### 4.3 审计

- `audit` 的一行：序号、时间、操作者、操作类型、对象、改动摘要、结果（成功或失败及原因）。
- 成功的命令：审计行与数据在同一事务里，不可能只有其一。
- 失败或被拒绝的命令：数据没有变化，审计行单独写入。
- **合并计数**：同一次运行里重复的同类记录（例如轮询同一个地址、反复被拒的同一种调用）合并成一行，记次数和首末时间。这样一个出错的插件不能把审计撑到无限大。
- 密钥和口令的值不进入命令内容，所以不会经由管线写进审计。插件自己把拿到的密钥写进别处的情况见 §13。

## 5. 树

树是内核机制，也是插件的扩展点。一棵树由清单声明，有两种来源：

- **存储树**：节点就是 `resources` 表里 `tree` 等于这棵树的行。资源树、环境树、配置树、数据源树属于这种。移动、排序、重命名、删除都是内核命令。
- **提供树**：节点由插件的代码按需给出（`children(父节点, 从第几条起)`）。文件树（内容来自硬盘）属于这种。子节点分批给出，一个文件夹里有几万个文件也不会一次全读出来。

另外，一个类型可以声明“我的子节点由我提供”。SQL 节点下的“历史”、综合节点下的资源引用，都用它，不需要新机制。

内核自带的树：

- **插件树**：从插件文件夹和各插件的状态节点得出。
- **收藏**（I.5）：内容来自 `resource_meta`。
- **已删除**：见 3.4。
- **运行记录**：跨所有资源的运行，按时间倒序；可以只看保留下来的结果。点一条在标签页中打开那次运行。

插件声明的树可以在清单里带上放在树工具栏的命令（例如“一层/两层分组”的切换）。

**集合**（按条件自动收集，I.10f）不是内核机制：由一个“集合”插件提供一种类型，body 里存查询条件，子节点由插件用 `resources` 的查询接口给出。第一版里内核的集合表取消。

节点交给界面时的形状（界面不认识类型，只画这些）：

```
{ key, label, icon, 可否展开, 状态(正常/停用/缺少插件/失效/冲突), 徽标,
  打开目标(见 §9), 右键项(命令 id 列表), 可否拖动, 接受哪些节点放入 }
```

- **拖拽**（I.0g）：是否可拖、能放到哪里写在类型的清单声明里，界面据此直接显示“可放/不可放”，不需要来回询问；放下后做什么由该类型所属的插件处理（存储树的默认处理是移动，由内核完成）。
- **从系统拖进来的文件**：拖拽的来源除了树上的节点，还可以是从访达拖进窗口的文件。接不接、接了做什么由放置目标所属的插件决定；被拖进来的文件对这一次操作可读。
- **右键**（D197）：右键项是命令，由节点所属类型的插件在清单里声明。
- **互不包含**（D163）：一个资源只属于一棵树；类型在清单里声明自己放在哪棵树里。
- **综合节点**（I.10f）：综合插件的类型，body 里是一组资源引用，子节点由插件提供。移除引用不动资源；引用的资源被删时显示为失效引用（§10）。

## 6. 参数、环境、配置

### 6.1 一套机制，三处使用

参数节点的 body：

```
{ description, params: { 名字: { type: text|number|boolean|list|secret|ref, value, based_on? } } }
```

`ref` 是对一条资源的引用（例如环境指定用哪个数据源，子环境继承）。

| 用处 | 存放 | 控制范围 |
|---|---|---|
| 环境 | 环境树的 `core:env` 节点 | 一个标签页 |
| 工作区配置 | 配置树的 `core:config` 节点 | 整个工作区 |
| 插件的启用、启用哪个版本、设置项、授权 | 每个插件一个 `core:plugin-state` 节点，显示在插件页 | 该插件在本工作区 |

因为它们都是资源，历史、恢复、审计都不用另做。

### 6.2 取值

- **环境**：`resolve(名字, 标签页)` 从该标签页选的环境节点开始，沿父链向上找，返回值和“来自哪一层”。找不到就返回“没有”，由插件决定怎么办（通常是让用户在表单里填，I.0f）。
- **工作区配置**：配置树没有“当前节点”，按名字取值。同一个名字在父节点和子节点里都有时，子节点的生效；两个互不为父子的节点不允许定义同名参数（写入时拒绝）。这样既保留父子覆盖（D162），取值又没有歧义。
- `secret` 类型只返回名字，值的取得见 7.5。

占位符的语法由插件定义（D182）。插件告诉内核“这个资源用到了哪些参数（名字、类型、说明）”，内核记进 `param_decls`，用来生成参数表单、悬停说明，以及在环境页自动列出参数。两个插件声明了同名但类型不同的参数时，环境页把它们并排列出并标明类型冲突，不替用户猜。

### 6.3 策略：只能加严

保留前缀的参数由内核解释。每个策略参数在内核里登记一条合并规则：

| 种类 | 合并 | 例 |
|---|---|---|
| 禁止类开关 | 任何一层禁止即禁止 | `protection.readonly`、`protection.no_export` |
| 允许名单 | 各层取交集 | `network.allow`、`process.allow` |
| 等级 | 取最严的一级 | `ai.policy` |
| 插件开关 | 各层都未停用才算启用 | `plugin.<id>.enabled` |

生效值由三段逐层合并：**插件状态节点 → 工作区配置 → 环境父链**。子层写了更宽的值不报错但不生效，界面标出“被上层限制”。

没有环境时怎么判断（拒绝优先）：

- **工作区配置这一层永远生效**，与有没有环境无关。
- **树上的操作**（右键删除、拖动、重命名）和命令面板里的操作不属于任何标签页，只按工作区配置判断。环境控制的是标签页内的运行条件（I.0b）。
- **没有标签页的运行**（定时、AI 发起）只能使用用户事先为它指定的环境；没有指定、或自己另挑一个环境的，拒绝运行。
- **标签页选的环境被删除了**：该标签页不能运行，提示重新选择环境；不会退化成“没有保护”。

具体有哪些策略参数、界面如何提示，在阶段 1 开始时列全（I.12 把它列为待设计）。

## 7. 插件

### 7.1 包、身份、版本

- 包 = 一个文件夹：`manifest.json`、逻辑入口 `main.js`、可选的界面入口、语言文件、可选的外部程序声明。
- 稳定 id `org.example.sql`；发布版 id `org.example.sql@1.2.0`（I.6）。
- 包放在 `plugins/<id>/<版本>/`，多版本并存。有哪些插件，以这个文件夹里实际有什么为准。为了在上万个插件时启动不变慢（I.6），主进程把读过的清单缓存在 `plugins/.index` 里，启动时核对每个 `manifest.json` 的修改时间和大小，变了的才重读；工作进程只读这份缓存；插件搜索查的也是它。缓存不是数据，删掉只会让下一次启动慢一点。
- 每个工作区自己决定：启用与否、启用哪个版本、是否固定（存在该插件的状态节点里，§6.1）。旧版本保留，可切回。资源与版本的关系见 7.6。
- 内置插件随应用发布，首次启动时装进同一个位置，之后与外部插件完全一样。应用更新带来内置插件的新版本时，新版本装在旧版本旁边；没有被固定的，按 7.6 的升级规则自动切到新版本。
- 安装时显示清单里的全部权限，用户确认后才能启用（D158）。**新版本要的权限比旧版本多时，升级前必须重新确认。** 安装、启用、停用、升级、卸载都是命令，进审计。
- 卸载一个插件或移除一个版本时，如果本工作区还有资源绑定着它，先列出数量并要求确认。确认后资源保留，显示为“缺少插件 某某@版本”，数据不动（I.6）。

### 7.2 清单（apiVersion "2"）

```
id, version, apiVersion, name, description, icon
main            逻辑入口
requires
  network       允许访问的主机；或声明“由本插件的连接资源决定”（7.5）
  secrets       要读取的密钥名；是否需要拿到密钥明文（7.5）
  files         是否需要文件能力（范围由用户在插件页授权）
  programs      要运行的外部程序的名字（7.5）
  resources     是否需要读取所有资源的基本信息（综合、集合这类插件用）
  plugins       依赖：稳定 id + 版本范围
contributes     本插件提供什么（全部是声明，不含代码）
  kinds         类型：字段、所在的树、图标、默认动作、页面、拖拽规则、右键项、是否自供子节点
  actions       动作：标题、适用类型、输入、输出类型、快捷键、是否运行前先保存、是否执行前确认（提示文字由框架统一弹出）
  pages         页面：操作区放哪些动作、结果区有哪些页签
  trees         树：名称、图标、存储树还是提供树、放在树工具栏上的命令
  outputs       结果区的输出类型
  resultActions 对内置输出类型加的结果区动作（如“分析”，见 9.5）
  nodes         自定义视图节点（见 §9.4）
  commands、menus   命令面板和“新建”下拉里的项
  locales       每种语言一份文字；语言插件另外提供外壳的文字
  settings      设置项（类型化参数的定义）
activation      除“被用到时”之外，还有什么情况需要激活本插件（如工作区打开后、某类资源发生变化）
exports         允许依赖方使用的扩展点
upgradesFrom    能接管哪些旧版本的数据（版本范围）
legacyKinds     接管第一版旧库里的哪些短类型名（3.1）
```

清单里的名称、标题都写成文字的键，按当前语言取值，缺失回退英语（I.1）。清单严格校验：未知字段、格式错误、id 重复都不加载，并在插件页给出原因（G.4）。

### 7.3 依赖与复用（I.0e）

B 依赖 A 并且 A 导出了某个扩展点时，B 可以：把自己的类型放进 A 的树；给 A 的类型加动作；用 A 的页面和输出类型；读 A 的类型的资源。没有导出的一律不可用。

依赖是否满足，按 A **当前启用的版本**判断。切换 A 的启用版本会让某个已启用的依赖方不再满足时，拒绝切换并列出这些依赖方，由用户先处理。

### 7.4 沙箱

- 每个已激活的插件版本在工作进程里有一个独立的 JS 运行环境（QuickJS）。里面没有网络、没有文件；除了少量与系统无关的基础工具（定时器、文字编码、网址解析、随机 id、摘要计算）之外，唯一能做的是调用宿主 API。
- 内存有上限；执行可被中断（激活超时、动作取消、死循环）。一个插件崩溃或超时不影响内核和其他插件。
- 插件之间不共享内存，只能经宿主 API 互相调用（并受 7.3 约束）。
- **大数据不进沙箱**：文件和网络传输的内容由宿主直接在“网络、文件、外部程序”之间搬运，插件只拿到一个句柄和进度（7.5 的 `transfer`）。几个 GB 的视频不会经过插件的内存。
- **惰性激活**：启动时一个插件也不运行。第一次需要某个插件的代码时（运行它的动作、渲染它的页面、展开它提供的节点，或发生了它在清单 `activation` 里声明的事）才激活。只显示树和列表不需要激活任何插件，因为图标、名称、拖拽规则都在清单里。
- **空闲回收**：一段时间没被用到、并且没有未结束的运行和未返回的宿主调用的插件，其运行环境被释放，下次用到再激活。插件不能假设自己一直在内存里，要保留的东西放 `storage`；要持续关心的事件写在清单的 `activation` 里，而不是只在代码里订阅。

需要技术验证的点：JS 引擎对 ES 模块、异步宿主函数、中断和内存上限的支持（阶段 0）。备选是纯 Rust 的 JS 引擎 Boa。

### 7.5 宿主 API

插件拿到的 `host` 对象。每个调用都进 §4 的管线或权限检查，操作者是该插件的发布版 id。

| 入口 | 作用 | 限制 |
|---|---|---|
| `resources` | 读、建、改、移动、删除资源；按条件查询 | 写：只限自己的类型。读内容：自己的和依赖导出的。读基本信息（id、名称、类型、图标、所在位置）：清单声明了 `requires.resources` 的可以读全部 |
| `params` | 按名字从当前标签页的环境取值 | 密钥类型只给名字 |
| `actions` | 调用动作 | 自己的和依赖导出的 |
| `runs` | 报告进度、读历史、附加内容（如 AI 分析） | 只限自己的资源的运行 |
| `storage` / `settings` | 插件自己的键值存储 / 读自己的设置 | 按插件、按版本隔离 |
| `secrets` | 使用密钥 | 见下 |
| `network` | 发 HTTP 请求 | 见下；每次调用进审计（I.10h），同类合并计数 |
| `files` | 列目录、读信息、读写文件内容、新建、改名、移动、复制、移到废纸篓、打开、在访达中显示、选择文件、文件夹或保存位置 | 三种范围：用户在插件页授权的文件夹（D184）；插件自己的目录；用户刚在系统对话框里选的、或刚从系统拖进来的文件，只对这一次操作有效。路径先规范化、解析符号链接再比较 |
| `transfer` | 由宿主直接搬运大数据：网络 → 文件、文件 → 网络、外部程序的输出 → 文件；返回进度，可取消 | 两端各自受 `network`、`files`、`process` 的限制 |
| `process` | 运行清单声明的外部程序，流式读输出，可取消 | 见下 |
| `events` | 订阅资源变化、运行结束 | 只收到自己能读的类型 |
| `ui` | 打开标签页、用系统浏览器打开、复制文字、通知 | 链接只允许 http、https、mailto；“用系统浏览器打开”只能在用户刚点了按钮触发的动作里直接执行，其他情况先让用户确认 |
| `i18n` | 取本插件当前语言的文字 | |

**网络白名单的两种来源**

- 写死在清单里的主机：适合只访问固定服务的插件。
- 来自连接资源：数据源、API 连接、HTTP 请求这类插件事先不知道用户要连哪里。它们在清单里声明“由本插件的连接资源决定”，并在类型定义里把某个字段标为“授权地址”。用户建立或修改这样一条连接资源，就等于授权了这个地址（I.10h“地址写入白名单”）；这次修改按权限变更记入审计。插件只能访问自己的连接资源里出现的地址。
- 两种来源都还要与环境的 `network.allow` 取交集。

**密钥**

- 插件能用哪些密钥：清单里声明的名字，加上它自己类型的资源里“密钥引用”字段指到的名字。别的插件用的密钥，它声明了同名也拿不到——除非用户在它自己的资源里引用了那个名字。
- 默认方式是**代入**：插件在请求头、请求体、外部程序的环境变量里写密钥的引用，宿主在发出时替换成真值。密钥的值不进入沙箱，插件拿不到，也就不可能写到别处去。
- **在表单里填密钥**：表单字段有“密钥”类型（数据源的密码、AI 的 API 密钥）。用户填的值由框架直接写进钥匙串，资源里只存名字和“已保存”，值不经过插件。
- 内核在一次运行期间把读过的密钥留在内存里，不会每次查询都去问钥匙串。
- 确实要用明文做计算的插件（例如对请求做签名）必须在清单里另外声明“需要密钥明文”，安装时单独提示。对这类插件，内核会把它拿到过的值从运行输出、进度消息和审计摘要里抹掉，作为补救；但不能保证拦住所有写法（见 §13、§17）。

**外部程序**

- 外部程序由插件负责：用哪个程序、哪个版本、从哪里来、怎么更新、怎么核对，都是插件自己的事。内核不下载、不校验、不管理它们。
- 内核只管四件事：
  - 插件只能运行清单里按名字声明过的程序；安装时把这些名字列给用户看，并明说“它会运行外部程序，这些程序可以访问这台电脑上你能访问的一切”，单独确认。
  - 程序只能来自两个地方：系统里装好的（`ssh`、`docker`、`bash`，内核在固定的几个位置里找，不依赖终端的 PATH，因为图形程序拿不到它；找不到时说明缺哪个）；或者插件自己的（随插件包带来的，或插件自己放进它的目录里的）。
  - 运行时可以设环境变量和工作目录；同一个插件的程序互相找得到（一个程序要调用另一个）；可以流式读输出、可以取消，取消时连同它启动的子进程一起结束。
  - 环境可以用 `process.allow` 禁止在某个环境下运行外部程序；每次运行进审计。
- 插件可以查询某个声明过的程序是否就绪。

**插件自己的目录**

每个插件在工作区里有一个自己的目录（`workspaces/<文件夹>/plugin-data/<插件id>/`），用来放它自己的程序、临时文件和缓存，不需要用户授权，别的插件读不到。它不是数据：不进历史、不导出、不同步；清空它只会让插件重新准备一遍。


- 用系统自带的限制手段进一步约束外部程序（只许访问指定文件夹和主机）是否可行，放在阶段 0 评估，不作为本设计的前提。

代码这一侧，插件只给清单里声明过的东西提供行为：

```ts
export default definePlugin({
  activate(host) {
    host.actions.handle("run", async (ctx, input) => { ... });          // 动作
    host.pages.handle("editor", { render(ctx) { ... }, onEvent(ctx, ev) { ... } });   // 页面内容
    host.kinds.handle("sql", { parameters(res) {...}, validate(body) {...}, migrate(body, from) {...},
                               describe(res) {...}, children(node, from) {...}, drop(ev) {...} });
    host.trees.handle("files", { children(node, from) { ... } });       // 提供树
  },
});
```

给清单里没有的东西注册行为会被拒绝。

### 7.6 资源绑定插件版本

规则：**资源标的是哪个版本的插件，就由哪个版本的插件来处理。**

- 每条资源记下它绑定的插件版本（`plugin_version`，如 `1.2.0`）。新建时绑定当前启用的版本。它与 `created_by`、`updated_by`（I.6）不同：那两个记的是“谁动过”，可能是内核或别的插件；这个记的是“这条数据归哪一版管”。
- 打开、显示、运行一条资源时，内核按它绑定的版本去找插件：字段定义、页面、动作、结果区页签都用那一版的。同一插件的几个版本可以同时各管各的资源，因为每个版本本来就在自己的沙箱里。

**哪些东西跟着资源走，哪些只取启用的版本**

| 跟着资源绑定的版本 | 只取当前启用的版本 |
|---|---|
| 类型的字段定义、图标 | 树、命令、菜单、“新建”入口、快捷键 |
| 该类型的页面、动作、右键项、结果区页签 | 设置项的定义和取值 |
| `validate`、`parameters`、`describe`、`children` | 导出的扩展点；依赖是否满足（7.3） |
| | 清单 `activation` 里声明的事件 |

所以旧版本只为它还管着的资源服务，不会在命令面板里多出一份“运行”，也不会有两套设置。

- **存储按版本分开**：`plugin_storage` 按“插件 + 版本”隔离，两个版本不会读到对方格式不同的数据。升级接管时，新版本可以读取旧版本的存储并转成自己的。
- **外部键的唯一范围**是类型，与版本无关。

**升级**

- 切换到新版本时，新版本接管旧数据。需要改数据的，由新版本自带的升级逻辑 `migrate(body, 旧版本)` 把它改成符合新版本的样子；不需要改的原样接管。接管之后，这些资源就绑定到新版本。
- 整个接管是一条批量命令（§4）：先在事务外把每条的新内容算好，再在一个事务里写入。任何一条算不出来或写不进去，全部不动，资源仍绑定旧版本、仍由旧版本处理，什么都没坏（I.6“失败时可以回退”）。
- 新版本在清单里声明自己能接管哪些旧版本。不能接管的那部分资源不动，继续绑定旧版本、由旧版本处理。

**回退**

- 把启用的版本切回旧版本：之后新建的资源用旧版本。已经绑定新版本的资源继续由新版本处理，不需要降级，也不删除（I.6）。
- **撤销某次升级**：每次升级接管记为一批。用户可以对这一批执行“撤销升级”：升级后没再改过的资源，退回升级前的快照并重新绑定旧版本；升级后改过的逐条列出，由用户选择保留现状（继续由新版本处理）还是退回。这才是“升级后发现新版本有问题”时真正的回退。

**其他情形**

- 从历史恢复一份旧快照、或恢复一条已删除的资源时，快照里带着它当时绑定的版本：那个版本本机还在，就恢复并绑定回那个版本；不在但当前版本能接管，就恢复并升级；两者都不行则拒绝恢复并说明需要哪个版本。
- 数据从外面进来（导入、git 拉取）同一规则：绑定的版本本机有，直接进来；没有但当前版本能接管，进来时升级；两者都不行的不写入，列出来并说明需要哪个版本的插件。
- 内核自己不会制造“没有插件能处理”的资源。只有用户卸载插件、或在文件夹里手动删掉某个版本时才会出现，此时资源显示为“缺少插件 某某@版本”，数据原样保留，把那个版本装回来即恢复正常。

## 8. 运行

动作执行、后台任务（导入文件夹、同步、拉取）是同一种东西：**运行**。

```
runs: id, 资源, 动作, 标签页, 环境, 操作者, 来源, 开始/结束时间,
      状态(running/success/error/cancelled), 参数, 当时的输入快照, 摘要(行数、消息), 错误, 输出, 是否保存
```

- 发起：`run.start(动作, 资源?, 输入, 标签页)` 立即返回运行 id；执行在后台，界面不卡（G.6、I.5）。
- **输入快照**：运行用的是用户眼前的内容，可能还没保存（9.3）。所以每次运行记下当时实际使用的内容。回看历史、显示“最终执行的文本”、“复用参数”都以它为准，不受之后修改的影响。
- 过程：插件用 `ctx.progress(...)` 报进度，内核把它作为事件推给界面（结果区和状态栏）。用户可以取消；插件被停用时它的运行自动取消。
- 结果：输出类型为 text、table、link、files、none，或插件提供的类型。内核校验输出与声明一致后存入 `runs`。结果可以直接给内容，也可以给一个数据文件的句柄（例如外部程序写出的 CSV），由宿主直接读取，几万行的结果不经过插件的内存。大的输出存 `blobs/`；表格在历史里默认只留前 1,000 行（可调），刚跑完的完整结果在这次运行被清理前可以导出。
- 保存的结果：用户可以把一次运行“保留”并起名字，它不受 200 次的限制；删除它时，挂在它下面的内容（如 AI 分析）一并删除。
- 历史：每个资源保留最近 200 次（I.5）。点历史 = 以这次运行为目标打开一个标签页（I.5“必须打开对应页面”）。“复用参数”= 用这次运行的参数再发起一次。
- 失败不抛到界面外：未知动作、插件停用、输入不合法、策略禁止、插件出错、输出类型不符，都是一条 `error` 状态的运行，原因留在结果区（I.0d）。
- 工作进程重启后，遗留的 `running` 记录改为失败，原因写明“应用中断”。
- 运行的开始和结束都写审计。
- **任务面板**：外壳提供一处列出所有进行中和刚结束的运行，显示进度、速度等插件报告的信息；可以取消、复制结果里的链接、清除已结束的。状态栏显示进行中的数量。

定时发起运行的调度机制不在本设计内（§16）；操作者来源里的 `scheduled` 和清单里的 `activation` 是为它留的位置。

## 9. 页面、视图、标签页、结果区

### 9.1 打开目标

标签页只是某个目标的显示（I.0b）。目标是一个地址：

```
resource:<id>          资源、分组、环境、配置项
plugin:<稳定id>         插件页
run:<运行id>            某次运行
node:<树>/<节点key>     提供树里的节点（如一个文件夹）
page:<插件id>/<页面id>  插件的独立页面（如欢迎页）
core:<页面>             外壳自带的页面（审计、已删除、冲突）
new:<类型>?parent=…    还没创建的资源：先在标签页里编辑，第一次保存时才创建
```

内核负责把目标解析成：标题、图标、面包屑（在树中的路径）、用哪个页面、操作区有哪些动作、结果区有哪些页签。界面只管画。

打开一个目标时可以带上初始的页面状态（例如从某次运行打开它的查询，并把当时的参数填进表单）。

环境页、配置页、插件页、审计页由外壳提供，直接用协议读写，不经过任何插件。

### 9.2 标签页上下文

每个标签页在内核里有一份上下文：`{ 目标, 环境, 页面状态 }`。

- 环境是内核认识的唯一字段：动作在哪个标签页发起，就用哪个标签页的环境取参数、判策略。
- 页面状态是页面所属插件自己的一小块数据（例如 SQL 页当前选的数据源），内核只负责保存和恢复。
- 标签的开合、顺序、固定属于界面状态。
- 这些都存在 `ui_state` 里，**按客户端分开**：每个桌面窗口、每个浏览器各有一个客户端标识，各有自己的一套标签页和布局，互不覆盖。同一工作区开两个窗口，或手机浏览器接入，不会把彼此的标签页冲掉。

### 9.3 页面内容：视图树

页面内容由插件的 `render(ctx)` 返回视图树，内核校验后交给界面画。`ctx` 里有已保存的资源、页面状态、环境、最近一次运行、当前语言。

基础节点仍是四种：form、table、text、link（D207）。表单的字段类型包括：文本、长文本/代码、数字、布尔、日期、时间（可带一组预设值，如“今天零点”）、枚举下拉、资源引用、密钥。文字节点可以按行标色（终端输出里错误流用另一种颜色）。在此之上需要两点改动，否则 SQL 页面做不出来：

1. **字段可以绑定**。form 的字段可以写 `bind: "body.sql"`，表示它编辑的是资源的这个字段。未保存的修改、未保存标记、⌘S 保存、关闭前询问都由框架统一处理。字段类型里有代码/长文本，可以声明“占满剩余空间”（I.7）。
2. **节点可以发事件**。按钮、表格行等可以带一个事件名，触发时内核调用插件的 `onEvent`，插件改页面状态，内核重新 `render`。

**未保存的输入何时交给插件**

输入时内容留在界面这一侧，不经过插件，保证打字不卡。以下三种时候会把当前未保存的内容送到内核：

- 运行动作时：用眼前的内容运行，并记入这次运行的输入快照（§8）。
- 页面声明了“内容变化后重算”时：停止输入约 300 毫秒后送一次，让插件重新算出参数表单（SQL 里新写了一个 `:name`，参数区就多一项）。
- 触发页面事件时：事件带上当前未保存的内容。插件可以返回“把某个字段改成什么”，由界面应用到未保存的内容上，仍然是未保存状态。“AI 生成 SQL”“格式化”这类功能走这条路，不需要绕过去直接保存资源。

**未保存时底层资源被别处改了**（git 拉取、另一个窗口、某个插件）：别处改的字段与自己正在改的不同，则自动合并，不打扰；改的是同一个字段，页面顶部出现提示，由用户选择保留自己的还是采用新的，不静默覆盖任何一方。

这是整个设计里对手感影响最大的一环，要在原型里实际量延迟（规划阶段 0）。

**信息面板**：每个资源页的右侧有一块由框架提供的信息面板，显示名称、所在位置、说明、标签、创建和最后修改的记录；可以收起，宽度可拖动并记住，不随内容变化（I.7）。插件不用自己画这些。

操作区不属于视图树：它由清单里页面的声明给出（哪些动作、顺序），框架保证位置、样式和“最多四个，其余进更多”（I.0h）。

### 9.4 插件自带界面

基础节点画不出来的（播放器），插件在清单的 `nodes` 里声明一个自定义节点，并提供一个界面入口文件。宿主把它装进一个隔离的 iframe：没有宿主页面的访问权、不能直接联网，只能通过消息收数据、发事件；设计 token 由宿主注入，保证外观一致。视频这类大内容不走消息：由宿主给出一个只对这个节点、这一份内容有效的临时地址，iframe 从这个地址取流。临时地址支持按范围读取（拖动进度条需要），在桌面窗口和浏览器访问时都可用。

“插件提供的标签页类型”（D175）= 内容只有一个自定义节点的页面，不是另一种机制。**标签页里面怎么排、怎么分栏、放什么控件，是这个页面自己的事，框架不管**：框架只给它位置、设计 token、与宿主通信的通道，以及保存它自己界面状态（如分栏的尺寸）的地方。基础节点拼不出来的页面（Vioros 的“列表 + 播放器 + 信息”）就用这种方式。此项在阶段 8 实现；但它是 Vioros 能否接入的关键，所以在阶段 0 先做技术验证（iframe 里播放宿主给的本机大文件并能拖动进度）。

### 9.5 结果区

- 页签由页面的清单声明决定，默认是“结果”和“历史”。插件可以加页签（如“最终 SQL”“AI 分析”），每个页签是一个对某次运行的 `render`。
- “结果”页签按输出类型选择画法：内置五种类型由框架画；插件提供的输出类型由该插件给出视图树。
- 工具栏右端的收起、展开、清空，以及高度的拖动和记忆，由框架提供（I.0h）。
- 对内置的表格和文字类型，**导出 CSV（带 BOM，没设目录时先问一次并记住）和复制由框架统一提供**，各插件不用各做一遍（I.7）。
- **别的插件可以给结果区加动作**：插件在清单的 `resultActions` 里声明“对表格/文字类型的结果加一个动作”，它会出现在所有这类结果上（例如 AI 插件的“分析”）。用户点了这个动作，这一次运行的结果才交给该插件；它平时读不到别的插件的运行结果。受 `ai.policy` 等策略约束。

## 10. 搜索与引用

- **搜索**（I.5、I.10a）：只在本工作区内。多个词必须同时满足；短词也能搜到（子串匹配，对中文有效）；可按类型过滤；排序依次为：名称命中优先、收藏优先、最近使用优先。同一入口也搜命令和插件清单。实现用全文索引（三字符分词，对中文有效）；不足三个字符的词退回模糊匹配。这是 sqlpool 已经验证过的做法，几千篇文档也够快。给插件的查询接口另有一种方式：命中任一词即可，按相关度排序，可限定类型和总量（AI 插件挑选相关文档时用）。
- **引用**（I.10a）：保存资源时，内核从类型定义里声明为“引用”或“可含引用的文字”的字段中取引用，写入 `refs`。只看声明过的字段，所以 SQL 正文里的 `[[1,2],[3,4]]` 不会被当成引用。文字里的 `[[名称]]` 在保存时解析成目标的 id 一并存下，之后目标改名引用不断，显示时用目标当前的名称。目标不存在或已删除时，`refs` 里保留这一行，界面显示为失效引用，不静默消失。

## 11. 语言与错误

- 内核不含任何界面文字。错误是 `{ code, 键, 参数 }`；界面用当前语言的文字文件把它变成句子，缺失回退英语，不显示键名（I.1）。
- 外壳的文字由语言插件提供；功能插件自带自己的文字（D193）。内核只提供“按插件、按语言、按键取文字，带回退”的查表。
- 英语是兜底：外壳自带一份英语文字。即使所有语言插件都被停用或损坏，界面仍然是完整的英语，不会出现空白或键名。
- 当前语言是工作区配置里的一个参数（D192），改了立即发事件，界面重画。

## 12. 协议

界面与工作进程之间只有一种协议。桌面窗口的消息经主进程转发到本机套接字；浏览器的消息经 WebSocket 到主进程，再转发：

- 请求/应答：`{ id, method, params }` → `{ id, result | error }`。
- 事件：界面订阅主题（某棵树、某个资源、某次运行、通知），内核推送。
- 连接建立时双方核对协议版本；不一致（例如浏览器里缓存着旧界面）时提示刷新，不带着不匹配的版本继续工作。
- 连接断开又恢复（工作进程重启、网络抖动）后，界面重新订阅并整体刷新一次，不假设中间没有漏掉事件。
- 方法按机制分组：`workspace.*`、`tree.*`、`resource.*`、`params.*`、`plugin.*`、`run.*`、`page.*`、`search.*`、`audit.*`、`secrets.*`、`ui.*`、`data.*`（导出导入）。
- 每个连接对应一个操作者和一个客户端标识，由主进程在转发时标明。本机桌面窗口直接可信；WebSocket 连接在正式的网页访问里需要口令和加密（阶段 9），开发和测试阶段只监听本机并使用一次性令牌。
- 另有一组主进程自己处理的方法 `app.*`：工作区的列表、新建、删除、打开，插件包的安装与移除。其中需要读写工作区内部数据的部分，由主进程转请相关的工作进程完成（2.1）。
- 密钥的值只能写入，协议里没有读出密钥值的方法。
- 类型以 Rust 为准，TS 类型由它生成并入库；`pnpm check` 检查生成结果是否最新（H 节“生成的文件随源码重新生成”）。

## 13. 安全边界

| 边界 | 做法 |
|---|---|
| 插件 ↔ 内核 | 两种运行模式下相同：沙箱内无任何系统能力；宿主 API 每次调用都检查清单声明、依赖导出、策略 |
| 插件 ↔ 插件 | 独立运行环境；存储按插件和版本隔离；只能用对方导出的扩展点；读别人的资源内容需要依赖导出，读基本信息需要单独声明 |
| 插件界面 ↔ 宿主页面 | 隔离的 iframe，只有消息通道和宿主给的临时取流地址 |
| 工作区 ↔ 工作区 | 多进程时是不同工作进程；两种模式下都是不同文件、不同钥匙串账户（按随机生成的工作区 id）；内核没有任何跨工作区的接口；主进程只转发，不合并不同工作区的数据 |
| 网络入口 | 只有主进程监听端口；工作进程只接受主进程的连接 |
| 网络 | 白名单来自清单或用户建立的连接资源；重定向逐跳复查；环境可以再收紧 |
| 文件 | 只在授权文件夹内；路径规范化、解析符号链接后再判断；删除默认进废纸篓 |
| 外部程序 | 只运行清单里声明过名字的；只能来自系统或插件自己的目录；安装时明示它不受沙箱约束；环境可以禁止；其余由插件负责 |
| 密钥 | 只在钥匙串；默认由宿主代入，值不进沙箱；要明文的插件须单独声明并确认 |
| 审计 | 成功的修改与数据同一事务；触发器禁止改删；同类记录合并计数 |
| 权限只能在本机放宽 | 见下 |

**权限只能在本机、由用户本人放宽**

插件的启用、授权文件夹、网络和外部程序的许可、保护类参数，都是参数，本来会随 git 和同步流动。如果不加限制，任何能往远程仓库推送的人（或另一台被攻破的设备）就能替这台电脑启用插件、扩大授权、关掉保护。所以：

- 插件状态节点（启用、版本、设置、授权文件夹）不进入 git 版本化和同步。授权文件夹是本机路径，本来也不该到别的设备上去。
- 环境和工作区配置里的策略参数可以随 git 和同步流动，但来自 `git`、`sync` 的改动如果是**放宽**（解除禁止、扩大名单、降低等级），不自动生效：先按原来较严的值执行，并在界面上列出，等本机用户确认。加严的改动直接生效。
- 用户自己从历史恢复属于本人操作，直接生效，照常记入审计。

## 15. 测试

- **内核**（`cargo test`，只用内存库和临时目录）：管线（事务、历史、审计一致；按字段的并发规则；没有变化不记；批量命令全成或全不成）、资源与树、删除与恢复（整批、永久删除）、参数取值与策略合并、清单校验、依赖、搜索、引用、导出导入（新 id 与引用改写）、迁移（含第一版旧库）。覆盖率 ≥ 80%。
- **版本绑定**：资源由它绑定的版本处理；两个版本同时各管各的资源且命令、设置只有一份；升级后资源绑定新版本；一条升级失败则全部不动且旧版本照常工作；撤销升级；回退后新版本的资源仍可用；从历史恢复旧版本的快照；导入本机无法处理的版本被拒绝。
- **沙箱与权限**：每一种越权各一个“被拒绝”的测试：未授权的主机、授权文件夹之外的路径（含 `..` 和符号链接）、别的插件的密钥、未声明明文却取密钥值、未导出的扩展点、未声明的外部程序、插件目录之外的程序、死循环、超内存、在 `validate`/`migrate` 里发起写入。
- **策略**：没有环境的定时或 AI 运行被拒绝；环境被删后标签页不能运行；来自 git 的放宽不自动生效，加严立即生效。
- **协议**：契约测试，TS 客户端与 Rust 两侧对同一组样例；版本不一致时拒绝；断线重连后状态一致。
- **进程**：工作进程被杀后自动重启且数据完整，遗留的运行被标为失败，它启动的外部程序一并结束；主进程被杀后工作进程自行退出；同一工作区不会被两个工作进程打开；连续崩溃时不进入重启循环。
- **运行模式**：协议测试在单进程、多进程两种模式下各跑一遍；界面测试在多进程下跑全量，在单进程下跑主要流程；一个和两个工作区时选对模式。
- **文件夹即事实**：手动拷入、改名、删掉一个工作区文件夹，或删掉一个插件文件夹后，启动能正确识别；`workspace.json` 丢失能恢复；删掉插件缓存后能重建；复制出的同 id 工作区得到新 id 且读不到原来的密钥。
- **sqlpool 对照**：sqlpool-parity.md 第 3 节逐行验收；内核源码里不得出现 sql、postgres、ssh、docker、psql。
- **Vioros 对照**：vioros-parity.md 第 3 节逐行验收；内核源码里不得出现 video、r2、bucket、yt-dlp、ffmpeg。
- **性能**：1 万条搜索 < 200 ms；冷启动到看到树 < 2 s；1 万个清单时启动只读缓存；重复导入 1 万个未变的文件不增加历史。
- **界面**：Playwright 用浏览器经主进程连真实工作进程；截图入库。另外每个阶段结束都真实启动桌面应用点一遍（H 节）。

## 17. 已知的取舍与风险

这些不是遗漏，是权衡之后接受的代价，列出来以便批准时知情。

1. **两种运行模式**（2.5）。收益是只有一个工作区时少一个进程。代价：协议测试要跑两遍；单进程下插件或内核崩溃会带走整个应用；新建第二个工作区后要重启才能并行；网页访问的监听和插件沙箱在同一个进程里。独立审查的意见是只保留多进程更简单。因为内核库与进程无关，这个决定以后可以改而不动内核和界面。
2. **外部程序不受沙箱约束**（7.5）。外部程序由插件负责，内核只限制“能运行哪些名字、从哪里来”，保证不了它运行起来做什么。靠安装时的明确提示和环境的禁止开关来控制。
3. **要密钥明文的插件**（7.5）。值一旦进入插件，内核只能事后抹掉它认得出的原样值，拦不住变形后的写法。所以把它做成需要单独声明和确认的权限，并尽量让插件用“宿主代入”的方式。
4. **历史存整条快照**（4.2）。占空间，未实测。
5. **多版本并存**（7.6）。带来了“哪些跟资源走、哪些只取启用版本”的一张表，是本设计里规则最多的一处。它换来的是升级和回退都不会让数据无人处理。
6. **页面由沙箱里的插件渲染**（9.3）。每次打开页面、每次重算都要过一次进程和沙箱，延迟未实测，是阶段 0 技术小样要回答的问题。
7. **审计只追加**（4.3）。第一版不提供清理，靠合并计数控制增长。长期使用后的体积未知。
