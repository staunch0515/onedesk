# OneDesk 的方向：把知识和业务都组织成书

> **状态**：用户 2026-11-26 和第⑧步一起讨论确定的长期方向。本文只记方向和原则，具体的每一步仍按 `book.md` §11 的做法：先写详细设计，用户确认后再开发。
>
> 相关文档：书的设计 `book.md`（D487，§0 是必须遵守的原则）、书的公开规范 `docs/book-spec/book-spec.md`、内核 `kernel-design.md`。

---

## 1. 出发点：书是人类伟大的发明

- 人类几千年来，能把**所有的知识和内容**通过书来组织和管理：教科书、手册、法典、辞典、账簿、病历、档案……
- 书之所以好用，是因为它有一整套成熟的**结构**：封面和版权页说明它是什么、谁出的、哪一版；目录给出结构和编号；正文按章节展开；附录、参考文献、索引、图表目录各司其职；版次和印次说明它怎么变化。
- 这些结构是几百年出版实践沉淀下来的，有国家标准（如 GB/T 12450 书名页和版本记录、GB/T 7714 参考文献著录），读者一拿起书就知道怎么读。

## 2. 互联网的问题：内容很多，但很乱

- 互联网上的知识数量远超任何图书馆，但**没有利用书的这种结构优势**：
  - 网页之间只有链接，没有“这是第几章、属于哪本书、哪一版”；
  - 同一份内容到处复制，不知道哪个是原本、哪个过时了；
  - 能计算、能运行的东西（表格、接口、脚本）和讲解它的文字是分开的。
- **OneDesk 要做的，就是把互联网上的内容拉回到书的结构上**：
  - 网页、笔记、接口、查询、数据……都是资源；
  - 把它们装订成书，按角色（封面、目录、正文、附录、参考文献……）组织；
  - 书和书之间可以引用、嵌入、计算，形成有结构的知识网。

## 3. OneDesk 的书比纸书多了什么

纸书只能看。OneDesk 的书是**结构 + 角色 + 可计算、可运行**，已经做到的：

| 能力 | 例子 | 在哪里 |
|---|---|---|
| 会算 | 公式页，读者代入自己的数 | 第④步（公式插件） |
| 能答题、判分 | 课本里的练习、测验、错题本 | 第⑤步（练习插件） |
| 能发布、有版次 | 版权页发布新版、重新印刷，学生版和教师版 | 第⑥步 |
| 能填写、签名定稿 | 病历这样的结构化文书，签名后只读，修订留痕 | 第⑦步（文书插件） |
| 能执行 | 运维手册一步步运行，等人确认，失败就停，留下记录 | 第⑧步（流程插件） |

## 4. 插件系统是根本

- OneDesk 的内核只认识**资源、插件、视图**；书、目录、公式、练习、文书、流程，**全部是插件**。
- 这一点和 Office 365 本质不同：
  - Office 也有加载项（Office Add-ins、VBA 宏），但它们只是挂在 Word、Excel 旁边的侧栏和宏，**改变不了“文档是什么”**；文档的结构、排版、计算都是写死在 Office 里的。
  - OneDesk 反过来，**“书能做什么”由插件决定**，没有上限。
- **公式和逻辑结构没有上限**：现在的公式插件很简单，但它只是担当“计算页”的一个插件。写新的插件，就能把任何公式、任何逻辑结构加进书里——统计模型、化学方程、电路计算、法条推理、业务规则……书本身一行都不用改，只是多了一种角色（`book.md` §0.3：加功能就是加角色）。

## 5. 两个服务器

### 5.1 书的服务器

- 作者（出版者）通过 OneDesk 把书**发布到服务器**上；
- 需要的人在服务器上找到书，**支付费用后使用**；
- 作者发新版、重新印刷，读者那里可以更新（第⑥步的版次、印次、只读副本，就是为这个准备的：现在是“发布成文件、导入文件”，以后换成服务器，书的格式不变）。

### 5.2 插件市场

- 插件也有一个服务器：**插件市场**；
- 作者发布插件，用户在市场里安装；
- 书依赖哪些插件，由书写明；打开一本书时，缺的插件从市场装上。

两个服务器都不在内核里：内核只提供“发布一棵子树”“导入只读副本”“安装插件包”这些通用能力，服务器是外面的系统。

## 6. 业务管理系统也做成书

- 最终目的：把**各种业务管理系统**也包装成书的样子来使用。
- 例子：
  - **库存管理系统**，就是一本**库存账本**（详细设计见 `book.md` §27）；
  - 财务就是一套账簿（总账、明细账、日记账）；
  - 病历就是病案（第⑦步的文书和档案）；
  - 合同管理就是合同簿；
  - 运维就是运维手册（第⑧步）。
- 原因：这些业务在没有计算机的年代，**本来就是用账簿、台账、登记簿、表单来管理的**，而且管得很好。它们的结构（账页、凭证、过账、结账、盘点、红字冲销）都是几百年会计和管理实践的结果。
- 做法和书一样（`book.md` §0）：先问现实里的账簿怎么做，书只负责装订，逻辑放进担当它的角色（账页、凭证、汇总表……），加功能就是加角色。

## 7. 内核一定要小

- OneDesk 要能在**多种设备上运行**（电脑、平板、手机……），所以内核一定要小。
- 每一次要给内核加能力，先问：
  1. 是不是非加不可（插件能不能自己做）？
  2. 是不是通用的（至少两种插件会用，不认识任何具体业务）？
  3. 够不够小？
- 到第⑧步为止加的内核能力，都是这样的小块：读子树、读嵌入内容、装订落点、连续显示、带参数的引用、可交互的嵌入、发布与只读副本、保留字段、文中控件、签章与快照、运行一个资源。

## 8. 一个人同时在多台设备上使用

- 一个人可能在几台电脑、手机上同时用 OneDesk，数据要怎么保持一致，**还要再讨论**；
- **要找到最好的方法后再实现**，不急着做；
- 已经有的基础：每个资源有版本号（`rev`）和修订历史，写入经过统一的管线，保存时会发现“别处改过了”（D374）；资源包有发布人、版次、印次。这些在设计同步时都会用到。

## 9. 和 Office 365 比较（2026-11-26 的看法）

| 方面 | Office 365 | OneDesk |
|---|---|---|
| 核心模型 | 几种固定的文档（Word、Excel、PowerPoint……） | 资源 + 插件 + 视图；书把资源按角色组织 |
| 扩展 | 加载项挂在旁边，改不了文档本身 | 插件就是一切，加功能就是加角色 |
| 知识的组织 | 一个个文件，靠文件夹和搜索 | 书：结构、编号、引用、嵌入、版次 |
| 计算和运行 | Excel 公式和宏 | 任何插件提供的计算和运行，结果写在书里、留下记录 |
| 业务系统 | 另买别的系统，再和 Office 对接 | 业务系统本身就是一本书 |
| 多人协作、云、多端 | 非常成熟 | 还没有（多设备的方法待讨论） |
| 排版、打印、格式互通 | 行业标准 | 还很简单 |
| 规模和生态 | 十几亿用户、几十年 | 刚起步；靠书的服务器和插件市场来建 |

- **模型上**：OneDesk 的“书 + 角色 + 插件”比 Office 的“固定几种文档”更有生命力，也更接近人类组织知识的方式。
- **差距**在协作、多端、排版、生态，是时间和规模的问题，不是方向的问题；书的服务器、插件市场、多设备的方法就是补这些的。
- **定位**：OneDesk 不是另一个 Office，而是“**新一代的书**”：知识、业务、计算、流程都用书来组织。

## 10. 接下来

1. **书的公开规范**：把书的结构、角色、接口、文字写法、资源包、版次印次、签章、流程写成一份公开的规范（`docs/book-spec/book-spec.md`），不依赖 OneDesk 的代码也能读写书。这是“新一代电子书标准”的第一步。
2. **库存账本**：第一个“业务系统做成书”的例子（`book.md` §27），用来检验“业务即书”的思路。
3. 之后再讨论：书的服务器和插件市场的协议、多设备的方法、导入现有的书（EPUB、Word 等）的导入插件、导出到旧格式（EPUB、PDF）。

# 第二部分：三个新方向的分析（用户 2026-11-26 提出）

> 用户提出三件事：① OneDesk 本身支持编程——在书里编程、测试、发布，以后程序的包装形式就是书；② 像 Claude Code 读写 GitHub 仓库那样，让 AI 读取、修改、管理、维护书；③ 书可以作为“收件箱”，收到的不是邮件，而是别人发来的、需要确认或签字、或带逻辑控制的页面。
>
> 下面按 `book.md` §0 的思路分析：先问现实里谁在做这件事，逻辑放进担当它的角色，内核只加通用而且小的能力。本部分是方向分析，不是详细设计；每一件真要做时，仍先写详细设计给用户确认。

## 11. 三件事其实是一件事

三件事放在一起看，是同一个循环：

```
   写（编程书、知识书、业务书）
        ↑                ↓
   收件箱（别人发来要你确认、    AI 读、改、维护
   签字、填写的；AI 的修改提案）   （提出修改，不直接改）
        ↑                ↓
        └── 发布（资源包、书的服务器、插件市场）──┘
```

- **书**是统一的容器：知识、业务、程序都是书。
- **修改**有统一的形式：不管是 AI 提的、同事提的、还是别人发来要你签的，都是“一份待你处理的东西”，你看过、确认、签字后才生效。
- **发布和传递**有统一的形式：资源包（K9）和以后的书的服务器。

所以三件事共用几样底层能力（§15），先把这几样做好，三件事都快。

## 12. 在书里编程：程序的包装形式就是书

### 12.1 先问现实

程序和书本来就很接近，历史上已经有过很好的例子：

| 现实 | 说明 |
|---|---|
| **文学编程**（Knuth 的 WEB、TeX 的源码就是一本书《TeX: The Program》） | 程序按讲解的顺序写成书，代码和说明在一起 |
| **Lions 的《UNIX 第六版源码评注》** | 一本书就是一个完整的系统：源码加逐段评注 |
| **技术手册、标准** | 接口说明、示例、测试用例、版本说明 |
| **软件的发行** | 版本号、更新说明、依赖、许可证——和版权页、参考文献、版次印次一一对应 |

### 12.2 角色对应

| 程序里的东西 | 书里的角色 | 说明 |
|---|---|---|
| README | **前言** | 这本程序书是什么、怎么用 |
| 代码文件、模块 | **代码页**（新角色） | 一页一个模块；说明和代码写在一起（文学编程）；按章组织（篇章就是目录结构） |
| 接口说明 | **目录、索引**（已有） | 目录给出模块结构和编号，索引收集函数和类型名，交叉引用就是“跳到定义” |
| 依赖 | **参考文献**（已有的角色，新用法） | 依赖哪些插件或书、哪个版本范围；就像引用别的书 |
| 测试 | **测试页**（新角色，借用第⑧步的步骤页和期望） | 每一页写测试用例和期望；**流程目录**一键跑全部测试，留下运行记录（测试报告） |
| 构建、发布 | **版权页**（已有） | “发布新版”就是发一个版本；版次、印次就是大版本、修补版本；发布记录就是更新说明 |
| 示例、教程 | 正文页、练习页（已有） | 示例能运行，教程能当场练 |
| 许可证、作者 | 版权页（已有） | |

**程序书 = 插件**：一本程序书发布出来，就是一个插件包；装进 OneDesk，它的类型、页面、动作就能用。插件市场上卖的就是这些书。

### 12.3 能做到什么

1. **OneDesk 的插件在 OneDesk 里写**：代码页写插件的代码，测试页跑测试，版权页发布到插件市场。这是“自举”——OneDesk 能生长自己。
2. **小程序、脚本、自动化**：一本“工具书”，每一页是一个能运行的工具（已有的脚本、命令、HTTP、SQL 就是雏形）。
3. **业务系统的定制**：库存账本这样的业务书，用户想改规则（比如加一种计价方法），写一页代码就是加一个角色。
4. **AI 辅助**：AI 读整本程序书（§13），按前言和说明写代码、补测试、修错误，提出修改，人确认后生效。

### 12.4 要的能力

| 能力 | 归谁 | 说明 |
|---|---|---|
| 代码页、测试页 | 新插件（程序书） | 代码编辑器已经有（设计系统的 `CodeEditor`）；测试复用第⑧步的步骤页、期望、流程目录 |
| **从书装配插件包** | 内核（通用，小） | 把一本书里按角色组织的代码页、清单、语言文件装配成插件包（就是 `.odplugin` 的文件），在“开发模式”下装上试用；不认识“程序书”，只认识“一棵子树按约定装配成文件” |
| 在沙箱里跑测试 | 内核已有 | 插件本来就在沙箱里运行；测试页的代码用同一个沙箱和假的宿主接口 |
| 版本和差异 | 内核已有修订历史；要补“两版之间的差异” | 资源的修订历史已经在；书的版次存档已经在（K9）；缺的是把两版的差别列出来（§15） |

### 12.5 要想清楚的

- **不替代所有编程**：Rust、大型 C++ 工程仍然用现有的工具；OneDesk 的编程先服务于**插件、脚本、业务规则、自动化**——也就是 OneDesk 自己的生态。这样内核仍然小。
- **分支和合并**：Git 有分支、合并。书的对应物是“副本”和“修订提案”（§13.3）：在副本上改，改好了作为提案交回原书，原书的作者确认后合进去。先用提案解决九成的需要，不急着做完整的分支。

## 13. AI 读写和维护书：像 Claude Code 对待 GitHub 仓库

### 13.1 先问现实

书在出版社里是这样维护的：**作者**写，**编辑**审稿、提修改意见，**校对**改错字、查一致，**排版**统一格式；修改意见写在**校样**上，作者同意才改进正文；每一版有**勘误表**。

AI 在 OneDesk 里担当的就是**编辑、校对、助理作者**：它读整本书、提修改意见，作者确认后才改进去。

### 13.2 为什么书比仓库更适合 AI

Claude Code 读 GitHub 仓库时，要自己从一堆文件里猜结构和意图。书天生就把这些说清楚了：

| 仓库 | 书 | 对 AI 的好处 |
|---|---|---|
| 文件和文件夹 | 目录：有部分、有编号、有顺序 | 一眼看出结构 |
| 文件类型靠扩展名猜 | 每页有**角色**：这是封面、这是练习、这是账页、这是单据 | AI 知道每一页“是干什么的”，改的时候不会越权（不会去改账页、不会改已签名的文书） |
| `README`、`CLAUDE.md` | **凡例**（新角色，实体书里就有：说明本书的体例、约定、写法） | 给读者也给 AI：这本书怎么写、有什么规矩 |
| 代码里的引用要靠搜索 | 引用、嵌入、索引、参考文献都是**显式的** | 改一处，知道哪里受影响 |
| 提交历史 | 修订历史、版次印次 | 知道什么改过、为什么 |
| 测试 | 期望、测验、流程目录 | 改完能自动检查对不对 |

**凡例**（体例说明）是这一节最值得加的角色：实体书在正文前常有“凡例”，说明本书的编排、符号、写法。它就是书的 `CLAUDE.md`，人读，AI 也读。

### 13.3 AI 改书：提出修改，人来确认

- AI **不直接改**书，而是提出**修订提案**：一组对若干页的修改（改哪几页、改成什么、为什么），像校样上的修改意见，也像 GitHub 的 Pull Request。
- 作者在提案上逐页看**前后对照**，接受、拒绝或改了再接受；接受后才写进书，记进修订历史（谁提的、谁同意的）。
- 已经有的基础：
  - MCP（D448）：外面的 AI 客户端（包括 Claude Code 本身）已经能通过 OneDesk 的 MCP 搜索、读取用户允许 AI 看的资源，运行只读动作；
  - AI 对话（D479、D480）：AI 的修改要“应用”后才进资源；
  - 签章（K6）：签了名的、结了账的，AI 改不了；
  - 保留字段（K10）、密钥：AI 看不到答案和密钥。
- 要补的是：**整本书的读取工具**（读目录、按角色读页、读引用和大纲、在书里搜索）和**修订提案**（§15）。

### 13.4 AI 能维护什么

| 书 | AI 做的维护 |
|---|---|
| 知识书 | 检查引用断了没有、编号和交叉引用对不对、索引漏了什么；按凡例统一写法；补摘要 |
| 课本 | 按课出练习题、检查答案和讲解、根据错题本出针对性练习 |
| 文书 | 按模板检查必填项、提示超出范围的值；写草稿（签名仍是人） |
| 账簿 | 对账：账页结存和汇总表对不对，单据和账页一致不一致；异常提醒（不能改已记账的） |
| 程序书 | 写代码、补测试、修错误、更新前言和更新说明 |
| 运维手册 | 运行失败时分析运行记录，提出修改步骤 |

### 13.5 本地和隐私

- 书在用户自己的设备上；AI 只看得到用户允许它看的书（`aiVisible`，默认关）。
- 用户可以用自己选的 AI（Claude Code 通过 MCP、或 OneDesk 内的 AI 对话）。
- AI 的每一次读写都记在审计里。

## 14. 书作为收件箱：别人发来的、要你处理的东西

### 14.1 先问现实

在没有电子邮件的年代，机关和企业已经有一套成熟的“收件”做法：

| 现实 | 说明 |
|---|---|
| **收文登记簿** | 收到的每一份文件登记：编号、来文单位、日期、事由、办理情况 |
| **传阅单、会签单** | 一份文件按顺序传给几个人，每人看过签字 |
| **审批单、请示** | 要你批：同意、不同意、批示意见 |
| **回执** | 收到后撕下回执寄回：“已收到” |
| **调查表、登记表** | 要你填写后交回 |
| **合同** | 要你签字盖章，一式两份，各执一份 |

这些和电子邮件不同：邮件只是“一段话”，而这些是**有结构、有逻辑、要你做一件事**的文件。

### 14.2 收件箱是一本书

- **收件箱 = 收文簿**（新角色）：一本书，里面每一项是别人发来的一件“来件”。收文簿的逻辑：登记（谁、何时、什么事）、待办和已办、提醒期限。
- **来件**是一个**小资源包**（K9 已有的格式）：发件人把一页或几页（要确认的文书、要签的合同、要填的表、要做的题）打包，写明**收件人**和**要你做什么**。
- 收到后是**只读副本**（K9），加上**你要处理的部分**：
  - 确认（“已阅”“同意”）；
  - 签字（签章 K6）；
  - 填写（文中控件 K4、表格字段 K15）；
  - 按逻辑走：条件、等确认、期限（第⑧步的步骤和比较）。
- 处理完，生成一份**回件**（只带你处理的部分：签了什么、填了什么、选了什么），发回发件人；发件人那边的原件上记下“某某已签”“某某的答卷”。

### 14.3 能做到什么（把前面每一步连起来）

| 来件 | 用到的已有能力 |
|---|---|
| 老师发作业、学生交回作答 | 练习（第⑤步）；第⑥步里推到以后的“交回作答”就是它 |
| 上级审签病历、合同 | 文书、签章（第⑦步） |
| 主管审核出库单 | 库存账本的单据、签章（第⑨步） |
| 运维发布需要负责人确认 | 流程目录的“等人确认”（第⑧步）——确认的人可以在别人的设备上 |
| 会签、传阅 | 一份来件按顺序传给几个人（流程目录定顺序） |
| 程序的修改提案（Pull Request） | 修订提案（§13.3）发到作者的收件箱 |
| AI 的修改提案 | 也进收件箱，和别人的一样处理 |

### 14.4 要想清楚的

1. **身份**：来件和回件要知道“是谁发的、是谁签的”，而且不能伪造。现在的签名人只是手填的名字（第⑦步），收件箱需要真正的身份：每个工作区（人）有一对密钥，来件、回件、签章用私钥签名，对方用公钥验证。这和书的服务器、插件市场的账号是同一套。
2. **传递**：不走电子邮件。第一版可以“发文件、导入文件”（和第⑥步一样）；以后走书的服务器：每个人在服务器上有一个“信箱”，服务器只转交加密的包，不看内容。
3. **来件里的逻辑是安全的**：来件里的页面由插件提供，逻辑在沙箱里运行；来件**不能带代码**，只能用收件人已经装好的、可信的插件（缺的插件从插件市场装，装之前要用户同意）；来件不能访问网络、不能读收件人的其他资源。
4. **不变成邮件**：来件必须有结构和要做的事；纯聊天、纯通知不是来件。这样收件箱永远是“待办”，不会被淹没。

## 15. 需要的通用能力（内核保持小）

三件事合起来，内核要加的通用能力只有几样，而且每样都至少两件事会用：

| 能力 | 用在哪里 | 说明 |
|---|---|---|
| **修订提案** | AI 改书（§13）、程序的合并（§12）、别人的修改意见（§14） | 一组对若干资源的修改，附说明；看前后对照，逐项接受或拒绝，接受后写入并记修订历史（谁提、谁同意）。不认识书，只认识“对资源的一组修改” |
| **两版之间的差异** | 修订提案、版次对比、程序书的版本、勘误表 | 资源级的前后对照（文字按行，字段按值），书级的“哪些页变了” |
| **身份和签名** | 收件箱、书的服务器、插件市场、签章 | 每个工作区一对密钥（私钥在钥匙串，规则 7）；签章、资源包、回件可以带签名并验证 |
| **寄出和回件** | 收件箱、交回作答、会签 | 资源包（K9）加上收件人、要做的事、回件的格式；回件只带处理的部分 |
| **从书装配插件包** | 编程（§12） | 一棵子树按约定装配成插件包文件，开发模式下安装试用 |
| **AI 读书的工具** | AI 维护（§13） | 给 MCP 和 AI 对话：读目录、按角色读页、读大纲和引用、在书里搜索、提交修订提案（不能直接写） |

都不认识“书”“作业”“合同”——符合 `book.md` §0.5 和 `direction.md` §7。

## 16. 建议的先后顺序

| 顺序 | 做什么 | 为什么先做 |
|---|---|---|
| 1 | **修订提案 + 差异 + AI 读书的工具** | MCP 和 AI 对话已经有，补上这些，AI 马上就能维护现有的书（课本、账本、手册），见效最快；修订提案也是后两件事的基础 |
| 2 | **凡例**（书的体例说明，给人和 AI） | 一个新角色，很小，但让 AI 维护的质量大大提高 |
| 3 | **身份和签名** | 收件箱、书的服务器、插件市场都离不开；先在本机生成密钥、签章带签名 |
| 4 | **收件箱（收文簿、来件、回件）** | 第一版走文件；先做“老师发作业、学生交回”和“上级审签”两个场景 |
| 5 | **程序书（代码页、测试页、从书装配插件包）** | 最大的一块；先从“在 OneDesk 里写 OneDesk 的插件”开始 |
| 6 | 书的服务器、插件市场 | 身份、寄出和回件都有了以后，服务器只是把文件换成网络 |

每一步仍按 `book.md` §11 的做法：先写详细设计，用户确认后开发。
