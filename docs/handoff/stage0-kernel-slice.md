# 阶段 0 技术小样：内核切片（kernel-slice）

日期 2026-11-15 · 代码在 `spikes/kernel-slice/`（一次性代码，结论才是交付物，未提交）

## 结论

七个问题里六个**可行**，一个**部分可行**（外部程序的系统级限制）。rquickjs 没有做不到的点，**没有启用 Boa，也没有跑 Boa 的对比**。

| # | 问题 | 结论 | 一句话 |
|---|---|---|---|
| 1 | ES 模块插件 + 无环境能力 + 只有异步 `host` | 可行 | rquickjs 0.14（quickjs-ng 0.16.2）直接支持 |
| 2 | 内存上限、死循环中断、激活超时、取消 | 可行，有三处要写进设计 | 见“意外” |
| 3 | 运行环境互相隔离；单个的代价 | 可行 | 建一个约 1–1.6 ms，空闲时约 180–200 kB |
| 4 | 工作进程 / 主进程 / 套接字 / 文件锁 / 两种模式同一套测试 | 可行 | 同一个测试函数跑两遍，都通过 |
| 5 | 关键路径延迟 | 远好于目标 | (a) p95 1.9 ms / 5.6 ms，(b) p95 2.3 ms / 3.0 ms，(c) 19 ms |
| 6 | Rust 类型生成 TS | 可行 | ts-rs 12，有过期检查脚本 |
| 7 | 用系统手段限制外部程序 | 部分 | 文件夹可以限制；主机名不行，只能“全禁 / 只许本机某端口” |

**测量环境（重要）**：Intel i7-1068NG7（8 线程）、16 GB、macOS 26.5.2、rustc 1.100.0。测量期间别的会话在同一台机器上编译，**系统负载 130–230**（8 核）。所以下面的数字是偏悲观的；空闲机器上只会更好，但我没有在空闲机器上重测。延迟测量用 release 构建；功能测试用 debug 构建。

## 1. JS 沙箱 —— 可行

- 每个插件一个 `AsyncRuntime` + 一个 `AsyncContext`。上下文只装语言内建（Date、Eval、RegExp、JSON、Map/Set、TypedArray、Promise）。测试列出了全部 63 个全局名，没有 `require / process / fetch / console / setTimeout / std / os` 等任何一个。
- 模块加载器只认插件自己的文件（内存里的表，只接受 `./x.js`）。`import "fs"`、`"node:fs"`、`"qjs:std"`、`"../other/index.js"`、`"/etc/passwd"`、`"https://…"`、动态 `import("fs")` 全部失败（有测试）。
- 出口只有一个 Rust 异步函数。一段引导脚本把它包成 `host.storage.get(...)` 这样的方法后交给 `activate(host)`，这个函数本身不挂在全局上。宿主收到的插件 id 由内核给，不由插件说。
- 已演示：`index.js` 以 ES 模块加载并 `import "./util.js"`；`activate(host)` 里 `await host.storage.set(...)`；处理函数里连续 await 两个宿主 Promise；Rust 用 JSON 字符串调用处理函数、拿回 JSON 字符串；JS 异常、未注册的处理函数、宿主拒绝的方法都变成 Rust 的错误值。
- 证据：`crates/kernel/tests/sandbox.rs` 的 `q1_*`；实现在 `crates/kernel/src/sandbox.rs`。

**意外**

- QuickJS 里**没有**定时器、文字编码、网址解析、随机 id、摘要计算。设计 7.4 说的“少量基础工具”要内核自己提供（宿主函数或一小段 JS）。本小样没有做。
- `eval`、`Function`、`SharedArrayBuffer`、`Atomics` 还在。它们出不了沙箱，但如果想禁掉动态代码，要另外处理。
- 保存 JS 函数句柄不能用 `Persistent`（它不是 `Send`，在锁外释放也不安全），要用 `ctx.store_userdata`。
- rquickjs-sys 自带 x86_64 和 aarch64 macOS 的预生成绑定，不需要 bindgen，只需要 C 编译器。**aarch64 我没有实际编译过**。

## 2. 限制 —— 可行，但有三处必须写进设计

| 项 | 结果 |
|---|---|
| 内存上限 | 上限 16 MB，插件不停分配 → 这次调用以“内存不足”失败；同一个运行环境接着能用，内核不受影响。无限递归同样只是这次调用失败 |
| `while(true){}` | 同步片段上限设 200 ms 时，200–203 ms 被打断（处理函数里、`activate` 里、模块顶层三种都测了） |
| 激活超时 | 设 500 ms 时 503 ms 返回；默认 10 秒的那条实测 10.004 秒 |
| 取消正在执行的处理函数 | 50 ms 时取消，52 ms 返回“已取消”；被取消的那段 JS 之后既没等到结果，也写不进任何东西 |

**意外（建议改设计）**

1. **“中断”要两套机制，缺一不可。** 引擎的中断回调只在 JS 正在执行时才会被问到，插件在等宿主调用时它不起作用。所以：同步死循环靠“看门狗”（每个同步片段限时），总时长和取消靠 Rust 这一侧放弃等待。
2. **看门狗打断的是“等待之后才开始的死循环”时，那个处理函数的 Promise 永远不会有结果**，而且引擎里会留下一个没人取走的异常，下一次调用会把它当成自己的错。小样里的处理：看门狗一响，直接让这个插件所有在途调用失败；每次调用前先清掉残留异常。看门狗也分不清是哪一次调用在转（同一个插件的多次调用会在 await 处交错）。**建议设计写明：看门狗触发或内存不足之后，丢弃这个插件的运行环境，下次用到再激活**（反正激活只要 1–2 ms）。
3. **JS 无法被“杀掉”，取消的真实含义是：结果作废，并且这次调用之后发出的宿主调用一律被拒绝。** 要做到后半句，宿主必须知道每个宿主调用属于哪一次调用，而 QuickJS 没有“异步上下文”。小样的做法是处理函数通过 `ctx.host` 调宿主（每次调用一个），激活时拿到的那个 `host` 只用来注册。**建议 7.5 的示例和接口按这个写**，否则取消之后插件还能继续写资源。
4. 内存不足在 JS 里是可以被 `catch` 的普通异常；上限只算 QuickJS 自己分配的内存，宿主这一侧为它准备的字符串不算。
5. 跑 JS 的是“当时在推进它的那个线程”。死循环的插件会占住一个线程直到看门狗响。测试里内核在插件空转期间仍在 150 ms 内答复了 `tree.page`（4 个线程）。**建议写明：插件代码与协议收发不在同一个线程上跑。**

## 3. 隔离与代价 —— 可行

- 插件 A 设了全局变量、改了 `Array.prototype`，插件 B 都看不到（测试 `q3_*`）。
- 50 个运行环境（release）：

| | 创建并激活 p50 / p95 | 空闲时常驻内存（每个） | QuickJS 堆（每个） |
|---|---|---|---|
| 空插件 | 0.89 ms / 1.23 ms | 约 180 kB | 100 kB |
| 演示插件（2 个模块、4 个处理函数） | 1.59 ms / 2.02 ms | 约 200 kB | 118 kB |

- 50 个空闲运行环境 2 秒内共用 CPU 0.1 ms（不空转）。
- **意外**：释放 50 个之后进程的常驻内存没有降下来（系统分配器不还给系统，只是之后可以复用）。“空闲回收”省的是可复用内存，不是任务管理器里看到的数字。

## 4. 进程模型 —— 可行

`worker`（一个工作区一个）、`mainhost`（主进程的替身）、`Supervisor`（启动、监视、重启）都在 `crates/kernel/`。

| 要求 | 结果 |
|---|---|
| 本机套接字 + 每行一条 JSON，`{id, method, params}` / `{id, result\|error}` + 推送事件 | 通过；连接后先核对协议版本，不一致返回 `versionMismatch` |
| 主进程消失，工作进程自己退出 | `kill -9` 主进程后约 7 ms 工作进程消失，锁也释放 |
| 工作进程崩溃被发现并重启 | 让它 `abort()`：那条请求得到 `workerGone`（不是挂住）；下一条请求自动等到新进程，从崩溃到拿到答复 72–73 ms（其中 50 ms 是故意的重启间隔）；界面侧收到 `worker.crashed`、`worker.restarted` 两个事件；崩溃前已提交的改名还在 |
| 同一工作区不能有两个工作进程 | 第二个以退出码 3 结束；`kill -9` 第一个之后锁立即可拿，新进程能正常打开 |
| 单进程模式走同一套消息 | 进程内同样是“一行 JSON 进、一行 JSON 出”；**同一个测试函数** `suite()` 对两种方式各跑一遍，都通过 |

`suite()` 覆盖：版本握手、未知方法、参数错误、树分页（不激活任何插件）、打开页面（惰性激活 + 视图校验）、重算参数、处理函数经宿主写内核存储、事件推送、按请求 id 取消、插件死循环时内核继续应答。

**意外**

- **macOS 的套接字路径最长 103 字节。** `~/Library/Application Support/onedesk/workspaces/<名称>/…` 很容易超。建议：套接字放在系统临时目录下的短路径，或者主进程建一对已连接的套接字、把一端交给子进程（后一种我没有试）。
- 文件锁用标准库的 `File::try_lock`（flock），不需要额外依赖。没有测试网络盘、iCloud 目录上的表现。
- 主进程在“连接已断、但还没收到子进程退出”的一小段时间里要把请求挂起等新进程，不能直接报错（第一版就踩到了）。
- 没做：工作进程启动的外部程序随它一起结束（进程组）；退避时间逐次加长写了但没有专门的测试。

## 5. 延迟 —— 远好于目标

200 次预热 + 1000 次顺序测量，release，负载 130–230 下：

| 路径 | 进程内 p50 / p95 | 经套接字 p50 / p95 | 目标 |
|---|---|---|---|
| 空请求（纯传输） | 0.004 / 0.005 ms | 0.095 / 0.181 ms | — |
| 树的一页 200 个节点（不经过插件） | 1.58 / 2.80 ms | 2.06 / 3.82 ms | — |
| (a) 打开标签页：沙箱里 `render` → 60 个节点（应答 5 kB）→ serde 校验 | **1.23 / 1.86 ms** | **1.90 / 5.56 ms** | p95 < 20 ms |
| (b) 重算参数：4 kB 未保存的 SQL → 插件找出 21 个 `:name` | **1.36 / 2.34 ms** | **1.70 / 3.02 ms** | p95 < 20 ms |

套接字下 (a) 的最大值是 28.6 ms（1000 次里的一次，p99 11.4 ms），我归因于机器负载，没有进一步验证。

(c) 冷启动，30 次，1 万行、第一页 200 个节点、零插件激活：

| | p50 / p95 |
|---|---|
| 多进程：启动工作进程 → 拿到第一页 | **19.1 / 21.8 ms**（其中启动到连上 16.1 ms） |
| 　工作进程内部：`main()` → 数据库已打开（WAL） | 2.9 / 4.6 ms |
| 　工作进程内部：`main()` → 开始监听 | 3.7 / 5.6 ms |
| 单进程：打开内核 → 拿到第一页 | **3.7 / 7.2 ms** |

目标是内核部分 < 500 ms，实际低一到两个数量级。**注意**：数据库文件刚写完就读，在系统的文件缓存里，这不是“开机后第一次启动”的数字；真实的应用还要加上 Tauri 和窗口的启动，这里没有量。

## 6. 类型生成 —— 可行

- `crates/protocol/src/lib.rs` 里的类型加 `#[derive(TS)] #[ts(export)]`，`cargo test -p ks-protocol` 生成到 `spikes/kernel-slice/bindings/`（24 个文件）。例：

```ts
// bindings/ViewNode.ts（自动生成）
export type ViewNode = { "type": "stack", children: Array<ViewNode>, } | { "type": "form", fields: Array<Field>, } | { "type": "table", columns: Array<Column>, rows: Array<Array<JsonValue>>, onRow?: string, } | { "type": "text", text: string, tone?: Tone, } | { "type": "link", label: string, href: string, };
```

- `scripts/check-types.sh` 生成到临时目录再与 `bindings/` 比较。实测：一致时退出 0；在 Rust 里给 `TreeNode` 加一个字段而不重新生成 → 打印差异、退出 1；改回去 → 退出 0。

**意外**

- 默认把 `i64/u64` 生成为 `bigint`，而它们在 JSON 里是普通数字。要设 `TS_RS_LARGE_INT=number`（放在 `.cargo/config.toml` 的 `[env]` 里）。代价：超过 2^53 的 id 会丢精度，协议里的 id 要么保证不超过，要么用字符串。
- ts-rs 不认识 serde 的 `deny_unknown_fields`，会报警告，要开 `no-serde-warnings`。
- 带字段的枚举分支要另外写 `rename_all_fields = "camelCase"`，否则 TS 和实际 JSON 都是 `on_row`（内核的校验第一次就因此拒绝了插件的输出）。

## 7. 用系统手段限制外部程序 —— 部分可行（实际在 macOS 26.5.2 上跑了）

| 手段 | 现状 |
|---|---|
| `sandbox-exec` + 规则文件 | 手册写着“已弃用”很多年，但在 26.5.2 上照常工作 |
| App Sandbox（签名时的权限声明） | 不适用：要给被运行的程序签名，不能按每次运行指定文件夹，对系统里现成的 `ssh`、`docker` 无从下手 |
| 网络扩展 / 端点安全 | 需要苹果批准的特殊权限和用户在系统设置里同意，不现实 |

用 `sandbox-exec` 实测（默认全禁，再放开）：

- 读允许的文件夹成功，读别处（含 `~/Documents`）“Operation not permitted”；写同理。
- 它启动的子进程继承同样的限制。
- 网络：全禁时连域名解析都失败；只放开 `localhost:18999` 时，连 18999 成功、连 18998 失败。
- **按主机限制做不到**：规则里写 `example.com:443` 或某个 IP，直接报 `host must be * or localhost`。

**建议**：维持设计现在的说法（不作为前提）。可以作为插件清单里的可选项：声明了的外部程序用 `sandbox-exec` 限制文件夹，网络只有“不限 / 全禁”两档。要做“只许某些主机”只能全禁后强制走内核开的本机代理，只对认代理设置的程序有效，不建议首期做。它是多一层防护，不是保证。**没有测**：`docker`（实际干活的是沙箱外的后台服务）、`ssh` 在规则下能否正常用；签名并公证后的应用里调用它。

## 对 `docs/redesign/kernel-design.md` 的修改建议

1. **7.4**：引擎确定为 rquickjs（quickjs-ng），删掉“备选 Boa”的悬念；补一句“定时器、编码、网址、随机 id、摘要由内核提供”。
2. **7.4**：把“执行可被中断”拆成三条：同步片段看门狗；每次调用的总时限；取消 = 结果作废 + 该次调用此后的宿主调用被拒绝。并写明“看门狗触发或内存不足后丢弃运行环境，下次惰性激活”。
3. **7.5**：处理函数通过 `ctx.host` 调宿主（按调用区分），`activate(host)` 的 `host` 只用于注册。
4. **7.4**：“空闲回收”可以保留，但不必复杂：激活 1–2 ms、每个约 200 kB，50 个插件全开也只有约 10 MB。
5. **2.2 / 12**：写明套接字路径的长度限制和放置位置；写明请求在工作进程重启期间的行为（在途的失败、新的等待）。
6. **12**：补充类型生成的三个约定（大整数为 number、字段改名、过期检查脚本）。
7. **§17 第 6 条**（页面由沙箱里的插件渲染，延迟未实测）：可以关闭，实测 p95 在 6 ms 以内。
8. **§17 第 1 条**（两种运行模式）：供决定时参考的数据——套接字每次往返多约 0.1 ms，多进程冷启动多约 15 ms。单进程模式“少一次进程启动”的收益就是这 15 ms。是否值得为它保留两种模式由你决定，我没有改任何东西。

## 没有实际跑过的

- Boa（rquickjs 没有做不到的点，所以没有对比）。
- Apple Silicon 上的编译和测量；空闲机器上的测量；磁盘缓存是冷的时候的冷启动。
- Tauri、窗口、界面这一段的耗时；经主进程转发两跳的延迟（这里是测试进程直接连工作进程）。
- 并发请求下的延迟（只测了顺序请求）；多个插件同时渲染。
- 空闲回收本身、插件之间经宿主互相调用、`transfer` 大数据搬运、外部程序进程组。
- 把已连接的套接字交给子进程的做法；网络盘上的文件锁。
- 第 7 问里的代理方案、`docker` / `ssh` 在规则下的表现。
